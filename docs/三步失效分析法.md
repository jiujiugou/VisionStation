# 三步失效分析法（AI 执行规程）

> 本文件是给 AI 的操作指令，不是给人读的叙述。执行任何一轮失效分析时，逐条遵守。
> 用户只验收三个产物文件 + 门禁退出码 0。不输出过程性解释。
>
> **本文件只写规则，不写现状。** 切片跑完的结果、未清偿清单、方法修订史，一律记在
> `docs/三步法落地记录.md`。规程不因项目进度而改；只有规则本身变了才改这里。
>
> 版本 v4 · 2026-10-19 · 本版为裁剪版，变动理由见 `docs/三步法落地记录.md` §6

## 0. 流程

```
阶段0 结构索引 → index.json
阶段1 分析    → FailureCatalog.json   [门禁1]
阶段2 约束    → RequirementCatalog.json [门禁2]
阶段3 验证    → VerificationReport.json [门禁3]
```

**何时跑**（不满足任一条就不跑，否则会退化成"有空就跑一遍"的项目制）：

- **判定逻辑变更**：阈值、换算、匹配段这类"拿数字做是非决定"的代码改了；
- **新增切片**：新模块 / 新设备 / 新工具首次纳入；
- **现场故障**：出现单测与日志定位不了的故障（静默错判、时序、状态残留）。

**何时不跑**：纯 UI 排版、依赖升级、注释与文档、已被分析器红牌拦下的格式类问题。
分析器能抓的形态（Dispose 模式、空 catch、null 违约）不占人工网格，走 `MACHINE_COVERED` 豁免（§2 第 6 条）。

五条铁律：
1. 追溯靠 ID：`F-xxx → R-xxx（多对多）→ V-xxx`，禁止用自然语言代替引用。
2. 门禁由 `gate_check.py` 判，退出码非零即停止，不得口头宣布通过。
3. UNKNOWN 不得默认安全：必须转为带 falsifier 的假设条目，最终以 UNVERIFIED 收尾。
4. **一条根因只登记一次**：同一 `path:line` 只许一条 FOUND，其他落格并入 `instances[]`。重复登记 = 重复计数，门禁阻断。
5. **条数必须过密度天花板**：`MAIN 条数 / KLOC` 超线即判定口径失控，退回阶段 1 归并，不许交付。

---

## 1. 阶段 0：结构索引

- 输入：项目源码。
- 操作：脚本 `build_index.py` 机械生成单元清单（有行为的类；纯数据载体/接口不计）+ 交互边。AI 只补语义字段（输入/输出/状态/依赖/资源），增删单元必须记录 deviation + 理由。
- 索引必须含 `coverage_claim`：显式列出未覆盖项（反射/DI、配置驱动调用、生成代码、第三方库内部、事件总线隐式耦合）。
- 每个单元必须记录 `path` 与 `loc`（有效代码行）：它是阶段 1 密度天花板的分母，缺了就无法判定条数是否失控。
- 网格总数 = (单元数 + 交互数) × 9。

## 2. 阶段 1：分析 → FailureCatalog

操作（顺序不可调，2 是归并，3 是分级，跳过任一步都会产出虚高清单）：

1. 每个单元 × 每条交互，按 9 类失效逐格检查：无效、缺失、延迟、重复、失败、阻塞、崩溃、资源耗尽、恢复失败。每格三选一：FOUND / N/A（`na_reason` ≥ 8 字符）/ 由类级豁免覆盖。
2. **归并**：先按 `path:line` 建主键。同一主键只允许一条 FOUND，其余格写入该条 `instances:[{target,category}]`，不得复制成新条目。同一句判断换个类别再写一遍，视为重复计数。
   注意区分：**两个不同 `path:line` 落在同一「单元×类别」是合法的**，不算重复。网格坐标是「单元×类别」，缺陷坐标是 `path:line`，多对一天然存在（如 `HealthChecker` 的配方校验与数据库校验同属 U19/无效，是两个独立根因）。门禁对此只做可见性输出；同一 `path:line` 出现两次才阻断。
3. **分级**：FOUND 必带 `tier`。
   - `MAIN`：有可执行验证手段的真实缺陷。计入问题总数，受密度天花板约束。
   - `OBSERVATION`（待定项）：理论可达、或只能靠人工审查判断的观察项。**不计入总数、单独成节**，但**必须给 `next_action` 指定出路**——只登记不给出路，等同于未判定，门禁阻断：
     - `PROMOTE`：升级为 MAIN，进阶段 2 走完整流程；
     - `DEFERRED`：本版不处理，必须同时给 `deferred_reason`（为什么不处理）与 `review_condition`（什么条件下强制重开）。
   - `reachability=THEORETICAL` 强制 `OBSERVATION`。
   - 门禁同时输出 `OBSERVATION : MAIN` 比值，超 1:1 警告——那是在用待定项稀释问题。
4. 每条 FOUND 必填：trigger、impact、`code_ref:"path:line@Symbol"`（脚本三重校验）、reachability、`danger_level`(S1/S2/S3)。
5. 未精读的单元不得填 FOUND，只能标 `unknown:true` 或 N/A（注明 index-only）。
6. **类级豁免**：若某类失效对某组目标整体不适用，写顶层 `category_exemptions`（一条覆盖多格，理由 ≥20 字符，`applies_to:["ALL"]` 或列目标）。禁止用小格 N/A 逐格敷衍——逐格写理由是虚高的直接诱因。
   豁免有两种性质，必须区分，不能混写：
   - **结构不适用**：该类失效在此目标上根本不存在（如无后台线程的目标不存在"崩溃"）。理由用自然语言写清机理。
   - `MACHINE_COVERED:` **机器已守**：该类失效的常见形态已被编译器或静态分析器常驻守卫，不再进人工网格重复登记。理由必须以 `MACHINE_COVERED:` 开头并列出规则号，例如
     `MACHINE_COVERED: S3881/CA1816（Dispose 模式）由分析器在每次 build 时守卫`。
     门禁会核对规则号在 `.editorconfig` 中存在且未设为 `none`——否则"机器守着"只是一句空话。
7. 出模后自检密度（§2.1），超线回第 2 步归并。

条目 schema：

```json
{id:"F-001", target:"U08", category:"阻塞", status:"FOUND|N/A",
 tier:"MAIN|OBSERVATION",                       // 缺失视为 MAIN（仅兼容旧产物）
 instances:[{target:"U20", category:"重复"}],     // 同根因的其他落格，不单独成条
 trigger, impact, code_ref, na_reason,
 reachability:"REACHABLE|CONSTRUCTIBLE|THEORETICAL",
 danger_level:"S1|S2|S3", unknown:bool, disposition?,
 next_action:"PROMOTE|DEFERRED",                // OBSERVATION 必填，只登记不给出路=未判定
 deferred_reason, review_condition,             // next_action=DEFERRED 时必填
 observable}                                    // danger_level=S1 时必填，见 §4
```

`observable` 的写法：**只准写现场能看见的现象，不准写判断**。合格示例：

> 拔掉网线后，界面在 10 秒内仍显示"已连接"，检测计数停止增长，日志没有任何错误。

不合格示例（写不出这一句的条目，说明它还没被理解成真实故障）：

> 违反可用性契约 / 不符合预期 / 存在状态不同步风险。

顶层字段：

```json
{entries:[...], category_exemptions:[{category:"资源耗尽", applies_to:["U19"], reason:"≥20 字符"}]}
```

门禁 1：网格全覆盖（F / N/A / 豁免三者之一）；code_ref 三重校验；**根因主键唯一**（重复即阻断）；THEORETICAL 不得为 MAIN；danger_level 必填；**S1 必须有 `observable` 且不得写成空话**；**OBSERVATION 必须有 `next_action`，DEFERRED 必须带 `deferred_reason` + `review_condition`**；`MACHINE_COVERED` 引用的规则号须在 `.editorconfig` 中生效（非 `none`）；**密度 ≤60 条/KLOC**；`OBSERVATION : MAIN` 超 1:1 警告。

### 2.1 密度天花板（唯一的反虚高硬约束）

| 项 | 值 |
| --- | --- |
| 分母 | scope 内被审单元的有效代码行（脚本统计，不许人工估算） |
| 指标 | `MAIN 条数 / KLOC` |
| 警戒 / 上限 | 30 / **60** 条/KLOC |
| 生效条件 | 分母 ≥200 行；小于此不判定（样本过小） |
| 依据 | 工控/嵌入式代码的工程经验是每 KLOC 个位数到十几条真实缺陷；超过 60 条/KLOC 必然混入了重复计数与理论项 |
| 附带 | 三份产物字节 > 源码字节 × 3 时警告：报告变成本体 |

阈值改动必须在落地记录中登记日期、理由与校准样本，不得临时放宽。

## 3. 阶段 2：约束 → RequirementCatalog

操作：
1. 每条 **MAIN** 状态的 FOUND 四选一：PREVENT / DETECT / RECOVER / ACCEPT。OBSERVATION 条目不强制进入本阶段。
2. provenance 四值：`PRODUCT_REQ / ARCH_RULE / CODE_AS_IS / ASSUMPTION`。CODE_AS_IS 不得作为 PASS 依据；ASSUMPTION 必带 falsifier。
3. 必填三要素：scope、trigger、criterion（写成可执行断言）。
4. 选 verification_method（七值枚举，见 §6）+ `command`。**所有手段都必须给命令，包含 CODE_REVIEW**——写不出可复现命令（grep / dotnet test / 复现程序）= “我看过了”，不算验证。
5. ACCEPT 必填 risk_owner + review_condition。
6. 分诊（见 §4）决定 control 与收尾方式。

条目 schema：

```json
{id:"R-001", from:["F-001"], provenance, control, statement,
 scope, trigger, criterion, verification_method, command,
 falsifier?, risk_owner?, review_condition?}
```

门禁 2：枚举合法；CODE_AS_IS 无 PASS 依据；三要素齐全；MAIN 故障全覆盖；S1/S2 的约束无 ACCEPT；ASSUMPTION 有 falsifier；ACCEPT 有 owner；**任何手段缺 command 即阻断**。

## 4. 危险分诊（对每条 FOUND 强制执行）

| 等级 | 判据（满足任一） | 处置 |
| --- | --- | --- |
| S1 危险 | ①数据丢失/不可逆；②静默错误判定（NG→OK 无告警）；③检查者自身失效（恒真判据、空表报全在线） | **必须修复**。禁 ACCEPT；禁 UNVERIFIED 收尾（换验证手段或改设计使其不可达）；收尾残留 FAIL/NOT_RUN 进未清偿清单并挂人 |
| S2 缺陷 | ①REACHABLE 且致功能失效/误告警/泄漏；②CONSTRUCTIBLE 但后果达 S1 | **必须修复**。禁 ACCEPT；残留项进未清偿清单 |
| S3 低危 | ①THEORETICAL；②仅日志/体验；③已被其他层拦截 | **兜底处理**。四选一：输入校验 / 默认值降级 / 告警 / ACCEPT(owner+复核)。目标：触发也不升级为 S1 后果 |

**定级必须接一个下游动作**，否则分级只是标签，不构成决策：

| 等级 | 谁审 | 形式 |
| --- | --- | --- |
| S1 | 独立上下文 | 新开一个没有历史记录的会话，只给 `diff` + `observable`，不给推理过程，让它回答"哪里会坏"。单人项目里的"二审"就是这个，不是找第二个人 |
| S2 | 作者自审 | 修完自读 diff，记录改动范围 |
| S3 | 免审 | 由 CI 与分析器兜底 |

S1 条目为什么强制 `observable`：它是唯一能让"二审"有输入的东西。没有现场可观测量，审查者只能看到一段自洽的推理，而自洽正是要检的东西。

改判：升级可自判；**降级必须用户确认**，记录理由+日期+改判人。
兼容：旧字段 `severity: H|M|L` 映射 H→S1、M→S2、L→S3，新产物一律 `danger_level`。

## 5. 阶段 3：验证 → VerificationReport

操作：
1. 对每条约束，**执行**其在阶段 2 选定的验证手段。正常/边界/故障场景。
2. 结果严格四态：PASS / FAIL / UNVERIFIED / NOT_RUN。禁止"基本通过"。
3. PASS 与 FAIL 必须附真实证据文件（门禁查文件系统）。
4. **结论分两类，不许混**：
   - **防线**（defense）：用例进了 `tests/`，每次 CI 都跑，改坏了会红。只有这类随版本持续有效。
   - **举证**（proof）：证据留在 `audit/*/evidence/`，证明"这一版这条已验"，换一版不会自动重跑。
   报告 `tally` 必须分 `defense` / `proof` 两栏计数。混在一起，会把一次性举证当成永久保障——Devices 切片 12 条 PASS 里，8 条是防线、4 条只是举证，合并计数时看不出来。
5. 修复纪律：**不得改测试、不得改判定标准、不得放宽阈值**。修复产出：最小复现 + diff + 重跑证据。FAIL 修复后不覆盖原记录，追加 `V-xxx-retry`。

条目 schema：

```json
{id:"V-001", req:"R-001", status:"PASS|FAIL|UNVERIFIED|NOT_RUN",
 evidence:"path", note, retry_of?}
```

门禁 3：每条约束 ≥1 记录；状态合法；证据存在；CODE_AS_IS 无 PASS；**`CODE_REVIEW` 不得判 PASS**；S1 无 UNVERIFIED 收尾；报告含 S1/S2 未清偿清单；`tally` 分 `defense` / `proof` 两栏。

## 6. 验证手段 × 工具 × 适用范围

手段分两档。**档位决定它算不算"验收"**，混成一张表 AI 会挑最省的那个。

### 6.1 必选档（按缺陷逐条选，四选一）

| 失效类别 | verification_method | 工具 | 适用 |
| --- | --- | --- | --- |
| 无效/缺失/重复 | UNIT_TEST | xUnit + dotnet test | 纯函数、配置校验、判定逻辑（ms 级） |
| 延迟/阻塞 | CONCURRENCY_TEST | Microsoft Coyote（系统化探索异步交错）；无则手写多线程桩 | 锁、单例、生产者消费者、生命周期交叠（s 级） |
| 失败/崩溃 | FAULT_INJECTION | 手工注入：只读目录、写满磁盘、拔设备、抛异常 | IO 边界、外部依赖失效 |
| 任何 | CODE_REVIEW | 无 | 兜底标注，**不算验收，最高只能产出 `UNVERIFIED`**。必须给可复现命令（如 `grep -n "TeardownDevice()" src/.../*.cs`） |

> **CODE_REVIEW 为什么不许 PASS**：`PASS` 的含义是"该失效已被证伪"，而 grep 只能证明"代码现在长这样"。允许它 PASS，未清偿项会从纸面上消失——Devices 切片 4 条正是这样被记成 12/12 的，实际它们一条都没验完。

### 6.2 升级档（按切片整体触发，不按条选）

| 手段 | 何时触发 | 工具 |
| --- | --- | --- |
| STRESS_TEST | 长时运行、句柄/内存增长是主要风险 | NBomber，测吞吐/延迟/稳定性（h 级） |
| RECOVERY_DRILL | 有看门狗、重启恢复、缓存重建需求 | 杀进程→重启→断言状态一致 |
| MUTATION_TEST | **不是缺陷验证手段**，是"测试有没有牙"的度量 | Stryker.NET（测试时长×N） |

成本顺序固定不可逆：单元(ms) → 并发(s) → 压力(h) → 变异(测试时长×N)。
变异靶点选择标准：**判定即产品**的代码（职责是拿数字做是非决定）。IO 胶水层不做，交给故障注入/恢复演练。

## 7. 信任结构（AI 不得混淆）

| 层 | 内容 | 来源 |
| --- | --- | --- |
| L1 | 覆盖计数、引用存在性、退出码、证据文件存在 | 脚本，全信 |
| L2 | 测试运行结果、复现输出 | 执行，可信 |
| L3 | AI 的因果推理、阈值合理性 | **待验收**，须逐条降级到 L2 |

门禁守 L1；方法的全部工作是 L3→L2 降级。

## 8. 局限（随报告输出）

9 类失效是规定检查维度，非故障全集；网格覆盖 100% 与漏掉真故障可同时成立；跨模块并发/传播故障只有集成验证能发现，须独立设计用例。

密度天花板只能拦"明显虚高"，**不能证明没漏**：低密度也可能意味着漏报，或用 `OBSERVATION` 把真缺陷挪出了统计。两个方向都要防——虚高看密度，漏报看对照组（真实现场故障痕迹）。`OBSERVATION : MAIN` 比值由门禁 1 自动计算并随每次输出，超 1:1 警告。
