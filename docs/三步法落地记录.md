### 7.1 本轮最值钱的三个观察

1. **「检查者自身失效」在这层是系统性的，不是孤例。** 自检结果不改变状态（F-A01）、
   重连的类型判断恒假（F-A05）、相机模式名与实际设备脱钩（F-A06）、

## 9. 方法修订史

### 9.1 v2.1：为什么加计数口径（2026-10-19）

对上一轮 35 条做机械统计（`audit/scripts/metrics.py`）后暴露四个问题，全部转化为门禁规则：

| 现象（实测） | 原因 | 对应规则 |
| --- | --- | --- |
| 35 条按 `path:line` 去重后仅 25 条，重复率 28.6% | 门禁只查"填没填"，不查"是否同一根因" | 铁律 4 + `instances[]` + 根因唯一阻断 |
| 密度 138.9 条/KLOC，去重后仍 99.2 | 全程没有分母，条数无从证伪 | 密度天花板 |
| 44% 格子是 N/A，理由多为敷衍 | 逐格写 N/A 成本高，编一条 FOUND 成本低 | 类级豁免 |
| 8 条理论项混在 35 条总数里虚增 | 没有分级，理论项与真实缺陷同权 | `tier: MAIN / OBSERVATION` |
| 产物 35.9 KB vs 源码 11.9 KB（3.0:1，含索引时 7:1） | 规程无体积约束 | 产物成本警告 |

**用新门禁回查旧产物：13 阻断 / 36 警告，退出码 1。** 旧产物不再合规——这是规则生效的证据，不是回归。

阈值（30/60 条/KLOC、3 倍体积、20 字符豁免理由、200 行最小分母）为工程经验值，仅经运维切片校准。全项目跑完后须复核。

### 9.2 v3：门禁自身的两个判定缺陷（2026-10-19，修复过程中暴露）

1. **已修复条目被排除在覆盖率之外**：原实现认为 `FIXED` 是历史记录、"不占格子"，结果修完一个缺陷覆盖率反而下降（63 → 43），逼着分析者去补凑数的 N/A。正确语义：`FIXED` 仍证明"这一格检查过"，计入覆盖；只是不计密度、不进"必须被约束处理"清单。
2. **N/A 条目与 FOUND 条目可同时覆盖同一格**：N-04/N-12 的理由写着"已由 F-007/F-038 修复"，却仍作为独立 N/A 存在——清单内部自相矛盾。已删除，语义并入对应 FOUND 条目。

教训：门禁的每一条规则都要能说明它防的是什么作弊。防不住的规则会变成额外的记账负担，甚至反向激励补凑数。

### 9.3 v3 补充：变异靶点选错了两批（2026-10-19）

第一批变异选了 Calibration + CoordinateMath，得分 91.43% 很好看。但规程 §6 自己写的标准是"**判定即产品**的代码（拿数字做是非决定）"，按这条标准，唯一该先测的是三个工具的判定段——DefectTool 判缺陷有无、DimensionTool 判超差、PresenceTool 判有无，判错就是漏检。选纯换算是因为它好测（无图像依赖、无浮点噪声），不是因为它是重点。

第二批补上判定段后得分只有 **58.86%**，说明判定段的测试密度远低于换算段。三轮补测后到 89.71%。

过程中暴露两个自己的错误：

1. **拿展示值当判定值**：`Metrics["MatchScore"]` 是 `Math.Round(maxVal, 4)`，我把它当阈值回灌，想测"得分恰等于阈值"的闭区间语义，结果实际比较的是未舍入原值（0.99996 显示成 1）。测试红了一次——是测试设计错，不是代码错。这类浮点精确边界在公共 API 上不可构造，最终在测试注释里写明"由代码审查保证"，不假装已覆盖。
2. **变异体存活不等于缺陷**：65 个存活里只有一部分是真问题。逐条分类后才看清：4 条数学等价、3 条浮点不可构造、4 条无断言可及。但也从中挖出 2 条真缺陷（F-C10 / F-C11），它们原来是 N/A 判断，被变异测试推翻——这是变异测试除了"验测试有没有牙"之外的第二个价值：**它会逼你逐行看那些从未被任何测试碰过的语句**。

教训：靶点选择要按"判错后果"排，不按"测试成本"排。选错了，得分再高也是自欺。

### 9.4 v4：裁剪三处职责错配（2026-10-19）

触发原因不是"文件太长"（161 行已经很瘦），而是 CI 跑起来之后暴露的重复劳动与自相矛盾。

**一、机器已守的形态还在手工登记。** CI 首轮报出 135 条告警，其中 `S3881`(8) + `CA1816`(10) + `S2486`(7) 与设备层手工登记的 F-D03 / F-D04 / O-D06 完全重合——分析器 3 秒给出的结论，人工网格花了一整轮。本版加 `MACHINE_COVERED:` 豁免类型：声明"机器已守"必须给规则号，门禁核对它在 `.editorconfig` 里存在且未设为 `none`。

**二、§6 把两种不同维度的东西并列。** 原表把 7 种手段平铺，`MUTATION_TEST`（验测试有没有牙）和其余 6 种（验缺陷被修没修）不在同一维度，并列会让 AI 误以为"这条缺陷可以用变异验"。本版拆成必选档（UNIT / CONCURRENCY / FAULT_INJECTION / CODE_REVIEW）与升级档（STRESS / RECOVERY / MUTATION），并按切片触发而非按条触发。

**三、`CODE_REVIEW` 能判 PASS，与规程自己写的"不算验收"矛盾。** 这是本次最实质的一改。grep 只能证明"代码现在长这样"，不能证明"失效已被证伪"。允许它 PASS，未清偿项就从纸面上消失了——设备层 4 条正是这样被记成 12/12 的。

后果必须记下来：**设备层验证结果从 12 PASS 变为 8 PASS + 4 UNVERIFIED**，未清偿清单随之变长。这不是退步，是把原本记在纸上的账记到了该记的地方。

**同时补三条，否则裁剪等于放水：**

- `OBSERVATION` 从"观察项"改为"待定项"，强制 `next_action`（PROMOTE 升 MAIN / DEFERRED 本版不处理 + 重开条件）。原来它不计入总数又不要求进阶段 2，成了唯一能免费往外挪问题的口子（设备层 6 条挂了一整轮，0 条处理）。
- S1 强制 `observable`，且禁止写成"违反契约""不符合预期"这类空话。理由：没有现场可观测量，独立复审只能看到一段自洽的推理，而自洽正是要检的东西。
- §5 的 `tally` 分 `defense` / `proof` 两栏：进 `tests/` 的才是防线，留 `evidence/` 的只是举证。

**新规则的生效验证**（不是"看代码觉得有"，是注入违规实测）：

| 注入的违规 | 门禁反应 |
| --- | --- |
| 待定项缺 `next_action` | BLOCK |
| `DEFERRED` 缺 `review_condition` | BLOCK |
| S1 的 `observable` 写成空话 | BLOCK（命中虚词表，如「不符合预期」「存在风险」） |
| `CODE_REVIEW` 判 PASS | BLOCK |
| `MACHINE_COVERED` 引用不存在的规则号 | BLOCK |
| S1 约束以 UNVERIFIED 结案 | BLOCK |
| `tally` 缺 `defense`/`proof` 分栏 | WARN |

顺带补上两条**规程早写着、脚本从没实现**的检查：`S1 无 UNVERIFIED 收尾`、`tally 分两栏`。规程声称检查而实际不检查，本身就是一种纸面合规。

**还修掉一处口径误报**：`U19/无效` 曾被报成"重复覆盖"。核对后是 `F-101`（`HealthChecker.cs:21` 配方校验）与 `F-001`（`HealthChecker.cs:74` 数据库校验）两个独立根因落在同一格。网格坐标是「单元×类别」，缺陷坐标是 `path:line`，多对一是常态，不该算重复计数。门禁改为信息输出（`U19/无效←F-001`），只有同一 `path:line` 出现两次才阻断。这条口径已写进 §2 第 2 条。

**旧切片的处理**：core / ops 两切片按旧规程收口，新规则让它们红出 19 条。逐条补齐（11 条补 `next_action` + 8 条补 `observable`），补的 `observable` 一律标 `observable_note: v4 补齐，由 impact 提炼，未经现场验证`——不假装是当时写的。其中两条只补去向、不动定级：**O-3**（清理静默跳过致磁盘写满）与 **O-C5**（测错孔却判合格），按 §4 判据②都已接近 S2/S1，定级需要人决定。
