# 产线闭环说明（VM → 上位机 → PLC）

> 2026-10-25 整理。目的：把"完整闭环长什么样、我们走到哪、缺什么"固化成一份可查的文档，
> 而不是每次会话从头推一遍。涉及 ST 契约的以 `docs/plc/触发与回写.st` 为准，
> 涉及 VM 报文的以 `docs/引擎集成-说明.md` 为准，本文不重复它们的细节。

## 1. 一句话定义

**闭环不是"软件跑通了"，而是"物理世界的一个动作，最终改变了物理世界，且中间每一环都留了痕"。**

三个角色分工固定，不要互相越界：

| 角色 | 定位 | 只做 | 不做 |
|---|---|---|---|
| VM（含相机采图） | 眼睛 | 回答"这张图好不好"（定位/测量/缺陷/判定） | 不指挥、不记账 |
| PLC | 手 | 节拍与执行（何时触发、何时剔除） | 不判断 |
| 上位机（VisionStation） | 账本 + 翻译 | 在 VM 与 PLC 之间转译信号；记录、追溯、良率、配方 | 不复制一份判定逻辑 |

判定权归 VM 的理由：公差/阈值是工艺知识，只应存在于 VM 配方一处。上位机再抄一份，
两边就会不一致，而且改工艺要改两个地方——这是显式的反模式。

## 2. 完整闭环的七步（标准形态）

| # | 步骤 | 谁做 | 载体 |
|---|---|---|---|
| ① | 物料到位 | 光电传感器 | X0 输入 → PLC |
| ② | 置触发位 | PLC | D100 = 1 |
| ③ | 读到并应答 | 上位机 | 轮询读到上升沿 → 清 D100 |
| ④ | 开始检测 | 上位机 → VM | 命令 VM 跑流程（或 VM 常驻自动） |
| ⑤ | 上报结果 | VM → 上位机 | TCP 9100：OK/NG + 数值 |
| ⑥ | 写回 + 心跳 | 上位机 → PLC | Modbus 写 D101 = 1/2，D102 每 100ms 自增 |
| ⑦ | 执行 + 报警 | PLC | Y 输出：NG 气缸推出 / OK 放行；D103/D104 计数；异常三色灯 |

**触发怎么发起，两种做法，没有对错：**

- **轮询握手**（本项目现状）：PLC 置 D100，上位机读到后清掉。好处是换 PLC 不用动一根线；
  代价是最多等一个轮询周期（100~200ms）。
- **硬触发**：PLC 直接给相机一根 I/O 触发线，延迟确定、抖动小，但接线固定、换平台要改线。
  追求节拍的产线用它；demo 和换型频繁的场合用轮询。

**心跳为什么必须有**：D102 是上位机每 100ms 写一次的自增数，PLC 侧监控它——上位机死了，
PLC 立刻停线报警。反之心跳断了也不能静默：否则"没人检测"会被默认当成 OK 放行。
**静默故障是视觉产线最贵的失效模式**（NG 件批量流出客户现场才发现）。

## 3. 寄存器契约（ST ↔ 上位机）

| 寄存器 | 方向 | 语义 |
|---|---|---|
| D100 | PLC 写，主机清 | 触发位。主机采用**自清除（接收应答）**语义：读到上升沿立即清 0，不等检测完成 |
| D101 | 主机写 | 结果位：1 = OK，2 = NG |
| D102 | 主机写 | 心跳，每 100ms +1。PLC 侧用 `<>` 比较（16 位会回绕，不能用 `>`） |
| D103 / D104 | PLC 累计 | OK / NG 计数 |
| D105 | PLC | 在线标志 |
| D106 | PLC 累计 | 触发计数（与主机收到的推送帧数对账 = 丢帧检测，**此对账尚未实现**） |

自清除语义的代价（写进代码注释了，这里再记一笔）：主机清了 D100 但随后处理失败时，
PLC 无法区分"收到并处理了"和"收到但处理失败"——只有 `LastError` 留痕。
这是"接收应答"的固有代价，选它换来的是 PLC 侧逻辑简单。

## 4. 单次检测时序与节拍预算

一次检测的时间账（t = 0 从传感器到位起算）：

| 步骤 | 耗时 | 性质 |
|---|---|---|
| 轮询等待 | 0 ~ 200ms | 最坏一个轮询周期 |
| VM 采图 + 流程判定 | ≈300ms | 典型估值，随流程复杂度变化，**需按实际流程实测** |
| TCP 上报 | 12ms | **本项目实测** |
| Modbus 写回 | ≈20ms | 典型估值 |
| **合计（最坏）** | **≈0.6s** | |

**死线公式**：`节拍预算 = （检测位到剔除位的距离）÷ 带速`。
例：带速 200mm/s、两工位相距 300mm → 预算 1.5s，最坏耗时 0.6s，余量 0.9s，安全。

余量不够时只有四个手段：① 轮询改硬触发；② VM 流程瘦身（少工具、降分辨率）；
③ 检测位到剔除位拉远；④ 接受"存疑件进待复核区"而不是直接剔除。

## 5. VM 报文格式

VM 4.2 用「发送数据」模块走原生分隔符（`OK;12.345\r\n`）或全局脚本走 JSON，
主机端 `VmResultParser` 按首字符自动分流两种格式。坑与细节见
`docs/引擎集成-说明.md` §3.3（E0000314 / E0000105 / AutoPlay / 输出至默认数据队列）。

## 6. 现状对照（2026-10-25）

| 环节 | 状态 | 依据 |
|---|---|---|
| VM → TCP → 上位机 → Modbus → PLC 写回 | **真跑通** | TCP 12ms 实测；D101 写回、D103/D104 计数器跳动均验证过 |
| PLC | **半真** | 跑在 AutoShop 仿真里，D100 由脚本/定时置位，不是传感器 |
| 相机/图像 | **半真** | MVS 虚拟相机链路已通，差镜头光源选型（方案问题，不是代码问题） |
| 光电传感器 | **缺失** | D100 现在靠定时/手动置位 |
| 剔除气缸 | **缺失** | D101 写了没人读——闭环断在物理层 |

### VM 模式的"半假触发"（已知设计缺口，面试可能被问穿）

组合根只要 `Plc.Enabled=true` 就注册 `PlcTriggerSource`，与引擎类型无关。VM 模式下实际发生的是：
D100 上升沿 → 清 D100 → `InspectionWorkflow` 发现引擎是 `IPushDrivenEngine` → **返回 null，
不检测、不写 D101**。D101 只由 VM 推送帧驱动。

也就是说：**PLC 的 ST 契约（"我触发→你检测→你给结果"）和真实数据流（"VM 常驻自己跑→
随时推→写 D101"）是分裂的**。D100 触发目前唯一真实的作用是让 ST 握手走下去 + D106 计数；
若 VM 侧停发，PLC 触发照样被应答却永远等不到 D101——静默故障的变种。

两个候选修法（**未定，待拍板**）：
- (a) 组合根按引擎分流：VM 模式不注册触发源，ST 改成只等 D101 + D102 心跳；
- (b) 保持现状，文档写明"VM 模式 D100 只是握手仪式，结果由推送驱动，两者无因果"（本文即此记录的载体）。
