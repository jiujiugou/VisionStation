# 代码导读 —— 从一行报文到一条记录

> 读者：要在这个仓库上改代码，或者要在面试里把它讲清楚的人。
> 目标：读完这七站，不打开代码也能说出「一帧结果从 VM 到界面经过了哪几个对象、各自负责什么」。

---

## 0. 先记住一句话

**这个程序不做检测。**

它只做四件事：接结果、记账、回 PLC、无人值守。
检测在 VisionMaster 的 `.sol` 流程里跑，相机归 VM 独占，上位机连相机库都不引用。

配套的三条硬规则，贯穿整个代码：

| # | 规则 | 落在哪 |
|---|---|---|
| 1 | **OK/NG 由 VM 给，上位机一个字不改** | `VmResultParser` 类注释、`AcceptExternalCoreAsync` |
| 2 | **空结果集判 NG**（没检 ≠ 合格） | `InspectionReport.IsOk` |
| 3 | **引擎不抛异常**，失败返回 `InspectionReport.Failure` | `IInspectionEngine` 接口注释、`Engines.Vm` 实现 |

第 3 条的现实含义：平台没授权、流程文件损坏，都变成"这一件没判出来 + 明确原因"，而不是"进程崩了"。

## 1. 分层与依赖方向

| 工程 | 职责 | 依赖 | 规模 |
|---|---|---|---|

依赖方向**单向**，只有 `App` 允许知道所有人。

## 2. 主线：一条报文的完整旅程

```
VM 4.2「发送数据」模块（TCP 客户端）
        │  一行文本：OK;1;1;1;1;1
        ▼
VmResultListener.HandleClientAsync          ← Devices/Vm/VmResultListener.cs:174
        │  ReadLineAsync（按行定界）
        │  先记 LastLineUtc，再 Dispatch     ← 链路通了但处理失败，也要算"通了"
        ▼
VmInspectionDriver.OnLine                   ← App/Services/Inspection/VmInspectionDriver.cs:241
        │  _busy 判重入，上一帧没完就丢并计数
        ▼
VmResultParser.Parse                        ← Engines.Vm/VmResultParser.cs:53
        │  首字符 '{' → JSON；否则 → 分隔符
        │  分隔符按位置对应配方的 vm.outputs
        │  顺带认出图像段（完整路径 / 目录+文件名）
        ▼
InspectionWorkflow.AcceptExternalAsync      ← App/Services/Inspection/InspectionWorkflow.cs:94
        │  ┌ AcceptExternalCoreAsync
        │  │  ① ImageFileResolver.Resolve   把"报文路径 / 兜底目录"翻成能读的文件
        │  │  ② Cv2.ImRead + MatBitmap      解码 + 缩到 1280 宽上屏
        │  │  ③ DrawAnnotations             把引擎给的 DrawRect/Circle/Contour 画上去 + OK/NG 水印
        │  │  ④ _repo.SaveAsync             入库（此时 report.ImagePath 已是真实文件）
        │  │  ⑤ _plcWriter.Write(IsOk)      写 D101：1=OK，2=NG
        │  └ 返回 InspectionRunResult（位图已 Freeze）
        ▼
VmInspectionDriver.Publish → SendToUi        ← 回 UI 线程
        │  发 InspectionResultMessage + ImageLinkStatusMessage
        ▼
ImagePanelViewModel / ResultPanelViewModel  ← 各面板订阅消息，各自更新
```

**这条链上只有两个线程切换点**：接收回调在 IO 线程，广播 `SendToUi` 回 UI 线程；中间那一段（解析→读图→入库→回 PLC）全在 `Task.Run` 里跑，不碰界面。

## 3. 七站阅读路线

按顺序读，每站控制在 20 分钟内。读完一站先别往下走，把"应该能回答"那栏在心里过一遍。

### 站 1 · 契约（约 400 行）

读：`Core/Engines/IInspectionEngine.cs` → `Core/Models/InspectionReport.cs` → `Core/Models/ToolResult.cs`

**看什么**
- 接口注释里为什么说"存在两个引擎"（历史语境），以及现在实际只剩一个实现。
- `InspectionReport.IsOk` 为什么要先判 `Count > 0`。
- `Results` 为什么用 `Dictionary<string, ToolResult>` 而不是三个固定字段。

**应该能回答**
1. 一个新引擎接进来，最少要实现什么？（`Name` / `Inspect` / `Reload` / `Dispose`）
2. 为什么 `Reload()` 返回 `string?` 而不是抛异常？
3. `IPushDrivenEngine` 是空接口，存在的意义是什么？
   （答：让自动循环跳过主动检测，否则每 2 秒往库里灌一条假 NG，良率被污染）

### 站 2 · 解析（约 380 行）

读：`Engines.Vm/VmResultParser.cs` + `tests/VisionStation.UnitTests/VmResultParserTests.cs`

**看什么**
- 两种格式的分流点在 `Parse` 的第 63 行：首字符是不是 `{` / `[`。
- `ParseDelimited` 里的 `consumed[]` 数组：图像段被"吃掉"后，后面所有值的下标要往前挪。
- `ParseVerdict` 的取值表：`OK/PASS/TRUE/1` → OK，`NG/FAIL/FALSE/0/2` → NG。
- 测试是最好的规格说明书，先读测试再读实现。

**应该能回答**
1. 分隔符格式为什么必须依赖配方 `vm.outputs` 的顺序？（没有字段名，只能按位置）
2. VM 只给总判定 NG、但各项都是 OK 时，代码怎么处理？为什么？
   （`ToReport` 末尾：以总判定为准，追加一条"VM 侧有未下发的否决条件"，不静默通过）
3. 「目录 + 文件名」两段路径的识别条件是什么？（前段有分隔符、后段无分隔符且有图片扩展名）

### 站 3 · 接收（约 250 行）

读：`Devices/Vm/VmResultListener.cs` → `Devices/Vm/VmLinkState.cs`

**看什么**
- 为什么上位机做服务端、VM 做客户端。
- `_lastLineUtcTicks` / `_connectedAtUtcTicks` 为什么用 `Interlocked` 存 long 而不是 DateTime。
- `Dispatch` 为什么必须 try-catch（一次数据库异常不能让接收线程死掉）。
- `VmLinkMonitor.Evaluate` 是纯函数：四态由三个输入决定，好测。

**应该能回答**
1. 端口被占用时会怎样？（`Start()` 直接抛，启动失败，不"起了但没在听"）
2. 超长行怎么处理？（1MB 上限，丢弃并记 Error，提示检查换行符）
3. 断流判定的基准时间是哪个？（`LastLineUtc ?? ConnectedAtUtc`：重连后头几秒不能误报）

### 站 4 · 驱动（约 320 行）

读：`App/Services/Inspection/VmInspectionDriver.cs`

**看什么**
- `_busy` 的语义：`1` = 上一帧还在处理，本帧直接丢弃并计数。
- 为什么丢弃必须说出来（`OnLine` 里的 `DropAlertThreshold`）。
- `CheckLink` 里"只在状态翻面时说话"：每秒报警会让人学会无视告警。
- `ReportTransition` 里 Error / Info 的分级：运行中断流是 Error，停机后没结果是 Info。

**应该能回答**
1. VM 推得比入库快，会怎样？（丢帧 + 计数 + 每 5 帧提示一次，不并发写 SQLite）
2. 停机时会不会刷告警？（不会，`_isRunning` 来自 `TriggerStateMessage`）

### 站 5 · 工作流（约 260 行）

读：`App/Services/Inspection/InspectionWorkflow.cs` + `IInspectionWorkflow.cs` + `Services/Imaging/ImageFileResolver.cs`

**看什么**
- `RunOnceAsync` 为什么是空实现（永远返回 null，不入库）。
- `AcceptExternalCoreAsync` 的五段：解析路径 → 解码缩放 → 标注 → 入库 → 回写 PLC。
- **为什么回写 PLC 在这一层而不是在 ViewModel**：两条判定路径（主动 / 推送），放上层只有一条会回写。
- `imageReason` 的四种说法：没图、VM 没给路径、路径不存在、解码失败。屏幕上都是黑的，处理方式完全不同。

**应该能回答**
1. 图画不出来会不会影响判定入库？（不会，catch 只记 warning，结论照常入库）
2. 兜底目录生效后为什么要改 `report.ImagePath`？（否则界面显示一张图、库里记另一张）

### 站 6 · 组合根（约 510 行）

读：`App/Composition/AppHost.cs` → `Services/ServiceCollectionExtensions.cs` → `Composition/AppOptions.cs`

**看什么**
- `Configure` 里六行注册的顺序：`AddDetection` → `AddVmLink` → `AddDevices` → `AddStorage` → `AddAppServices` → `AddViews`。
- `InitializeAsync` 的八步顺序，尤其"为什么 VM 监听要放在建表之后"。
- `StopAsync` 的六步关闭，以及为什么顺序不能颠倒。
- `LoadRecipe` 的三级回退：`.active` 指针 → `Recipe:Path` → 内嵌资源。

**应该能回答**
1. 设备连接为什么不在 DI 工厂里做？（解析一个对象不该有"打开设备"这种副作用）
2. 关闭时为什么先停在途帧、最后才释放容器？（否则在途帧会落到已释放的 DbContext 上）
3. 配方里写了 `Vm` 以外的 `engine` 会怎样？（`InspectionEngineFactory` 直接抛，不静默回落；`Onnx` 已被删掉，写它也只是一个未知引擎）

### 站 7 · 界面（挑着读，约 800 行）

读：`Messages.cs` → `ViewModels/ImagePanelViewModel.cs` → `ViewModels/InspectionPageViewModel.cs` → `ViewModels/SidebarViewModel.cs`

**看什么**
- 消息中枢的 8 种消息：`InspectionResultMessage` / `TriggerStateMessage` / `LogMessage` / `ImageLinkStatusMessage` / `EngineerModeMessage` / `SessionChangedMessage` / `VmLinkStatusMessage`。
- `ImagePanelViewModel` 的 NG 保持窗口：2 秒，只在"下一件到达时"判断是否过期，不起定时器。
- `InspectionPageViewModel.RunFrameAsync` 的防重入与丢弃节流。
- 侧边栏的 `engineerOnly`：图像来源页只有工程师模式可见。

**应该能回答**
1. 面板之间怎么通信？（`WeakReferenceMessenger`，不互相持有）
2. 为什么位图必须 `Freeze()`？（跨线程绑定）
3. VM 模式下点「开始检测」会怎样？（走 `RunOnceAsync` → 记一条 Debug → 返回 null，不入库）

## 4. 六个必须能讲出来的决策

面试时被追问"为什么这么设计"，这六条是能展开的。

| # | 决策 | 依据 | 反方观点怎么答 |
|---|---|---|---|
| 1 | **放弃 VM SDK，改 TCP 中转** | VM 4.2 SDK = net461 + `System.Runtime.Remoting`，.NET 8 进程加载即崩 `0xC000000D`；net48 能跑但要管理员权限 + 抄 VM 配置树 | "SDK 能拿到图像和模块结果" —— 是，但换来一个只能在特定 .NET 版本、特定权限下活的宿主 |
| 2 | **支持两种报文格式** | VM 4.2「格式化」模块保存含 `{}` 的文本报 `Lang_FmtTestFail`，走 JSON 要写全局脚本 | "为什么不定死一种" —— 定死 JSON 等于要求现场必须写脚本，多一道门槛 |
| 3 | **PLC 触发用自清除（读沿即清 0）** | PLC 只需置位一次，不用等检测完成再复位；换 PLC 不用改线 | "处理失败时 PLC 不知道" —— 所以有 D106 触发计数对账（**尚未实现**，如实说） |
| 4 | **丢帧必须计数并说出来** | 节拍 50ms、单帧 200ms 时每 4 次丢 3 次，界面上完全看不出来 | "直接排队不行吗" —— 排队只会让界面永远追不上现场 |
| 5 | **NG 只保持 2 秒，不永久钉住** | 停在历史帧上的监视器比黑屏更危险——操作员会以为产线停了 | "NG 就该一直留着" —— 有缩略回看兜这一层，主图必须反映现场 |
| 6 | **图片由 VM 存盘，上位机只读** | TCP 拿不到图像本身，只有 SDK 能；上位机再存一份就是两份真相 | "那 VM 目录被清了怎么办" —— 所以有"图像来源"兜底目录 + 四种缺图原因 |

## 6. 别在面试里说错的四件事

1. **"我自己实现了模板匹配/霍夫圆/Blob"** —— 已删除，三个工具类和 `Pipeline`、`IVisionTool` 都不在了。现在是 VM 做判定。
2. **"我用海康 MVS SDK 采图"** —— 相机层 2026-10-26 整体删除，代码里没有任何相机采集。
3. **"D100 触发会启动一次检测"** —— 不会。VM 模式下 `RunOnceAsync` 直接返回 null，D100 目前只走握手 + D106 计数。这是**已知缺口**，主动说比被问出来好。
4. **"ONNX 在运行时兜底"** —— 不能。ONNX 整条线已于 2026-10-27 从仓库删除（引擎工程、离线跑批工具、权重、数据集、相关测试），本程序只有 VM 一条判定路线。

## 7. 现状缺口（知道比不知道好）

| 缺口 | 影响 | 位置 |
|---|---|---|
| D100 触发不驱动检测（"半假触发"） | 触发链路只握手不检测 | `InspectionWorkflow.RunOnceAsync` |
| D106 触发计数未与接收帧数对账 | 没有"漏帧率"这个数字 | 未实现 |
| 断流文案拼接 bug | "已 从未收到结果，已经 没有收到…" | `VmInspectionDriver.FormatSince` + `ReportTransition` |

## 附：启动与关闭的完整顺序

**启动**（`AppHost.InitializeAsync`）
1. 绑定并校验配置（失败写 crash.log，非 0 退出）
2. 加载配方（`.active` → `Recipe:Path` → 内嵌）
3. `DeviceManager.ConnectAll()`（PLC 连接）
4. `HealthChecker.RunAll()` 五项自检（失败只记日志，**不弹模态框**）
5. 建表 `EnsureCreatedAsync`
6. 良率补基数（今日 OK/NG，重启不归零）
7. 建出厂管理员（失败只降级"不能登录"）
8. 启动 VM 监听 `VmInspectionDriver.Start()`
9. 记第一条审计 `AppStart`

**关闭**（`AppHost.StopAsync`，8 秒预算）
1. 停触发源 → 1.5 停 VM 监听 → 2 应用级取消 → 3 等在途帧 → 3.5 刷界面日志 → 3.8 审计 `AppStop` + Flush → 4 释放容器（后台线程）→ 5 `Log.CloseAndFlush` → 6 通知看门狗正常退出
