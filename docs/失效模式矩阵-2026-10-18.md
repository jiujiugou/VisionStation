# 失效模式矩阵 —— 软件质量到底能"保证"到什么程度

> 扫描日期：2026-10-18 · 扫描范围：`src/` 全部 19 处 `catch`、全部外部资源调用点、业务主链路
> 用途：回答"业务流程没问题、没有 bug、兜底完善"这三件事各自该怎么验、验到什么程度停

---

## 一、先纠正问题本身

**"保证软件没有问题"是不可能的。** 任何工程师说这句话，只有两种可能：没做过生产系统，或者在骗人。

软件工程里真正能保证的只有三条，而这三条**都可以验收**：

| 能保证的 | 含义 | 怎么验 |
| --- | --- | --- |
| **失败是显性的** | 任何异常都不会变成"看起来正常的结果" | 故障注入，逐个制造 |
| **覆盖是可见的** | 哪些验过、哪些没验，有清单能查 | 矩阵表 + 覆盖率报告 |
| **回归是被拦住的** | 改动不会悄悄毁掉已验过的部分 | 黄金样本库 + CI |

不能保证的：零 bug、真实硬件的光学与电气行为、形式化的并发正确性、100% 覆盖率。

所以这个问题的正确问法是：**"我要保证的是这三条里的哪一条？哪一条现在还是空的？"**

---

## 二、四种手段，各管一段缺陷

这是最容易被忽略的一点：**没有一种手段能覆盖全部缺陷，缺任何一段就有固定盲区。**

| 手段 | 能抓住 | 抓不住 | 你的现状 |
| --- | --- | --- | --- |
| 单元测试 | 逻辑分支写错、边界条件 | 集成边界、真实输入、资源耗尽 | 44 个（Core + Storage + 评估逻辑） |
| 黄金样本回归 | 改动引入的精度退化 | 数据集未覆盖的类别与输入 | 105 张，刚建立 |
| **故障注入** | **错误路径的实际行为** | 逻辑正确性 | **0** |
| 长跑 + 对账 | 内存/句柄/磁盘泄漏、数据漂移 | 单次正确性 | 0 |

### 你的最大空洞不是"没写测试"，是错误路径从来没被执行过

全项目 19 处 `catch`，每一处都只写过一次，**没有任何一处被实际跑过**。
这些代码和死代码的区别只有一条：理论上会执行。

一个从来没执行过的错误处理分支，你无法知道它：
- 是不是根本不会触发（catch 的位置放错了，异常在更外层就被吞了）
- 触发之后行为对不对（日志级别？要不要停机？状态怎么恢复？）
- 会不会自己抛异常（catch 块里的代码同样可能崩）

**这就是"故障注入"这一格必须填上的原因 —— 它测的不是逻辑，是"出事的时候你到底会怎么样"。**

## 三、业务流程正确性：缺的不是测试，是不变式

业务链路：`采图 → 检测 → 标注 → 存图 → 存库 → 显示`

"业务流程没问题"这句话要有意义，必须先回答三件事。现在三件都是空的：

### 3.1 状态机不存在

全系统只有一个 `_isProcessing` 布尔量。没有 Idle / Running / Stopping / Faulted 的区分，于是这些问题没有答案：

- 急停按下时，正在检测的那一帧算不算数？
- 停止后再次触发，允许吗？
- 存图失败了，系统算"正在运行"还是"故障"？

**一个布尔量表达不了四态。** 这不是 bug，是模型缺失 —— 而模型缺失的地方，测试也写不出来。

### 3.2 不变量没有写下来

哪些事必须永远成立？举例：

- `DB 里每条检测记录的图片都能在磁盘上找到`
- `屏显 OK + NG 总数 == DB 记录数`
- `Pipeline 输出的每个 DrawCommand 坐标都在图像范围内`
- `报告里每个工具结果的名字都能在配方里找到`

**不变量不写下来，就无法被验。** 写下来的每一条都能变成一个断言或一个测试，而且成本极低。

### 3.3 "部分失败"没有定义

存图成功、存库失败，这一帧算成功还是失败？

现在的实际行为是：图留在磁盘上，库里没记录，日志里一行 warning。**没有任何地方定义过这是不是可接受的行为。**

产线上这种孤儿图片会越积越多，磁盘慢慢满，而没有人知道为什么。

## 四、实测失效点清单

等级定义：
- **P0** = 错误结果会流到下游，或造成数据不一致 —— 出了事你不一定知道，知道了也查不到根源
- **P1** = 会让人"不知道出事了" —— 系统继续跑，但已经不在你以为的状态
- **P2** = 演练级，可以不管

| # | 位置 | 触发条件 | 当前行为 | 后果 | 等级 |
| --- | --- | --- | --- | --- | --- |
| **F1** | `ImageStoreService.Save` ← `MainViewModel` | 磁盘满 / 无写权限 / 路径被占 / 编码失败 | 返回值被直接丢弃，`Cv2.ImWrite` 失败只返回 false 不抛异常 | NG 图静默永久丢失，无人知晓 | ~~P0~~ **已修** |
| **F2** | `Pipeline.cs:153` | 工具内部抛异常（模型崩、空 ROI、内存不足） | 捕获 → 转成 `ToolResult.Ng` | **机台故障被记成工件 NG**，等于把设备问题记到产品账上 | **P0** |
| **F3** | `App.xaml.cs:96` | 启动自检任一项失败 | `MessageBox` 警告后**继续启动** | 5 项全红也能进主界面开检，界面看起来一切正常 | **P0** |
| **F4** | `App.xaml.cs:LoadRecipe` | 配方 JSON 损坏 / 反序列化异常 | 吞异常 → 用内置兜底配方 | 兜底配方的 ppm/公差/ROI 与实物不符 → **所有尺寸判据都是错的**，但系统在正常工作 | **P0** |
| **F5** | `MainViewModel` 采图分支 | `Capture()` 返回 null | 记 warning + `return` | 连续失败无计数、不停机，100 次失败 = 100 行 warning | P1 |
| **F6** | `ToolFactory.cs:79` | `models/neu-det.onnx` 缺失 | `Debug.WriteLine` + 返回 null，工具不注册 | 少一个检测工具，但**自检 5 项全绿**（自检没有"模型文件"这一项） | P1 |
| **F7** | `HealthChecker.CheckDatabase` | DB 被锁 / 损坏 / 磁盘满 | 只检查**目录可达** | 自检通过，但第一帧写库就抛异常 | P1 |
| **F8** | `MainViewModel` 存库 | `SaveAsync` 抛异常 | 外层 catch 记日志 | 图片成孤儿；屏显 OK/NG 已在内存累加，与库不一致 | P1 |
| **F9** | `MainViewModel:129` | 触发频率 > 处理耗时 | `if (_isProcessing) return` | 被跳过的帧无计数 —— 漏了多少件查不到 | P1 |
| **F10** | `HealthChecker.CheckDevices` | 相机在线但出不了图 | `online == total` 即通过 | 自检绿，点开检必失败 | P2 |
| **F11** | `OnnxYoloTool.ExtractCandidates` | 类别表与权重类别数错位 | `objectnessOffset` 为正不触发异常，直接读错通道 | 静默输出垃圾结果，不报错 | P1 |

### 三条最硬的，展开说

**F2 —— 把故障伪装成结论。**
`Pipeline` 里工具抛异常 → `ToolResult.Ng` → 报告 NG → 存库 → 屏显 NG。
从数据上看，这件工件是"被测出不合格"；而事实上是**检测器自己崩了**。
后果比漏检更隐蔽：产线会把好件当坏件扔掉，而且统计数据里看不出来。

正确形态：区分 `ToolResult.Ng`（工件不良）和 `ToolResult.Fault`（检测失败）。故障不出报告，出报警。

**F3 —— 自检只警告不阻断。**
自检的价值全部来自"能不能拦住开检"。只弹一个 MessageBox 然后照常进入主界面，等于自检只是给操作员看了一眼。
正确形态：自检失败 → 进入只读/调试模式，**禁止开检**，直到问题解决。

**F4 —— 兜底配方比崩溃更危险。**
`LoadRecipe` 解析失败时返回一个内置配方，让程序能启动。这是典型的 demo 思维：保住演示。
但兜底配方的 ppm 是 15.0、公差 0.50、ROI 是写死的坐标 —— 与当前实物大概率不符。
结果是：**系统正常启动、正常检测、输出一整套错误的判定**。
正确形态：配方加载失败就是启动失败。没有配方，系统不该假装能工作。

## 五、优先级：按"改完买到什么保证"排，不按"重要程度"排

### 第一批 · 1 小时 —— 把"故障"和"不良"分开

修 F2 + F6 + F7。改完你能说出这句话：

> "我的系统不会把机台故障记到工件账上；模型缺失或数据库不可用时，自检会当场拦住。"

这是三条里最值钱的一条：**它决定了你的数据能不能被信任。**

### 第二批 · 半天 —— 让"配置不通"变成"装不成能工作的样子"

修 F3 + F4。改完你能说：

> "自检不过就不允许开检；配方坏了启动就失败，不用兜底配方糊过去。"

### 第三批 · 1 天 —— 故障注入，把 19 个 catch 全部跑一遍

五个必须制造的故障，每个都要有明确预期行为和自动化断言：

| 注入的故障 | 预期行为 |
| --- | --- |
| 拔掉相机（`IsAvailable=false`） | 停止检测 + 明确报警，恢复后自动续跑 |
| 删除模型文件 | 自检失败，禁止开检（不是少一个工具） |
| 锁住数据库文件 | 写库失败有明确升级路径，不吞成一行 warning |
| 磁盘写满 | 存图失败连续 N 次后升级为 Error 并提示 |
| 把配方 JSON 改坏 | 启动失败，报出具体哪一行 |

改完你能说：**"这五条故障我都实际制造过，行为是明确的。"** —— 这句话比"我写了 44 个单元测试"更能证明工程成熟度。

### 第四批 —— 长跑 + 对账

- 72 小时连续跑：内存、句柄、磁盘、DB 体积的增长曲线
- 对账：屏显 OK+NG 总数 vs DB 记录数 vs 归档图片数

## 六、明确不要保证的东西

| 不做的 | 原因 |
| --- | --- |
| 零 bug | 不存在。追求它只会让你把时间花在改注释上 |
| 真实硬件的光学/电气行为 | 需要设备和现场，仿真不出来。诚实标注为待验证 |
| 形式化并发证明 | 成本远超收益。用"一条线程写、加锁读"的设计约束替代 |
| 100% 覆盖率 | 覆盖率是症状不是目标。追 80% 往往是测 getter |
| 全部 19 个 catch 都写测试 | 只测"会导致静默错误"和"会导致停机"的那些，其余靠代码评审 |

## 七、面试怎么讲

> "我不说我的代码没有 bug，我说的是三件事。**第一，失败是显性的**——我把所有可能导致静默降级的地方都改成了显式告警，比如存图失败原来返回值直接丢，`ImWrite` 又只返回 false 不抛异常，磁盘满了会安静地丢掉全部 NG 图，这个我改了并加了连续失败计数。**第二，覆盖是可见的**——算法层有 44 个单元测试加 105 张黄金样本做回归，但硬件相关的那部分我明确标成未验证，不装。**第三，我知道自己的边界**——这套是工作站不是在线设备，业务状态机只有一个布尔量，这块我知道该怎么改但需要真实产线才能验证，所以没动。"

这段话的杀伤力在于：**它把"我没有 bug"这种无法验证的主张，换成了三个可以当场追问的具体事项。**
