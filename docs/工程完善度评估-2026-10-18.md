# VisionStation 工程完善度评估（对标 NitroGateway）

> 评估时间：2026-10-18。所有数字来自对两个仓库的实测（git ls-files / wc -l / find），不是估计。
> 用途：判断 VisionStation 距离"别人敢放到产线上运行的软件"还差多少，并给出可执行补全路线。

---

## 一、结论先行

**按同一把尺子：VisionStation 41/100。**

但真正有价值的不是这个分数，而是差距的**性质**。它分三类：

- **A 类 · 一天能补完的基建**（缺 CI、缺构建配置、ADR 没进仓库）——这是账面差距的大头，但不产生护城河。
- **B 类 · 视觉工程特有、NitroGateway 也没有的**（黄金样本库、漏检/过杀率、标定误差量化、模型版本治理）——这一维 NitroGateway 得 0 分，因为它是网关不是视觉。**谁补上这一维，谁才算真正跨过门槛。**
- **C 类 · 不该照搬的**（Docker、18 个项目、出厂门禁、web 双壳）——照搬是纯浪费时间。

去掉视觉精度那一维（NitroGateway 不适用），归一化后：**VisionStation 49%，NitroGateway 89%。**
换句话说：普通工程基建这块，你差着四倍；但你有一个 NitroGateway 永远拿不到分的赛道没开始跑。

## 七、"真正的工程"三条可验收判据

1. **任何一次 push，CI 必须绿**——测试通过 + 构建无新增警告。
2. **改算法前后，黄金样本库的漏检/过杀变化必须可量化**——不能只说"我觉得更准了"。
3. **换一台空机器，一条命令能跑起来**——SDK 锁定 + 自包含发布 + README 写清。

满足这三条，即使代码量只有现在的一半，也比现在更接近"别人敢放到产线上运行的软件"。

## 九、放到产线还差什么（生产就绪度）

### 9.1 先定性：这是两个不同的东西

现在的 VisionStation 是一个**工作站**：人在旁边、按一下检一张、结果看屏幕、数据落 SQLite。
产线要的是一个**在线检测设备**：没人管、自动跑、自动分选、失效了自己知道。

差距主要在架构假设，不在功能数量。五条本质差异：

| # | 维度 | 工作站（现状） | 在线设备（产线） |
| --- | --- | --- | --- |
| 1 | 触发源 | `ManualTrigger` / `TimerTrigger` | PLC / 光电 / 编码器硬触发 |
| 2 | 帧与工件对应 | `Capture()` 取最新帧，无工件 ID | 每帧绑定工件 ID，FIFO 队列处理 |
| 3 | 处理跟不上时 | `_isProcessing` 直接跳过 = **漏检** | 排队缓冲，结果延后到分选位 |
| 4 | 结果出口 | SQLite + 存图 + 屏幕显示 | 写 PLC 位 / 缺陷码 → 气缸分选 |
| 5 | 失效自检 | 启动查设备 / DB / 路径 | 标准件校验 + 漂移报警 + 计数对账 |

### 9.2 为什么"取最新帧"在产线上是错的

`HikCamera` 现在是连续采集（`TriggerMode` OFF）+ `Capture()` 消费最新帧。这套在演示时没问题，上产线会出事：

- 连续模式下相机按固定帧率出图，工件在运动，**你拿到的永远是"最近一帧"，不是工件到位那一帧**。每帧里工件位置都不同，检测结果和具体哪个工件的对应关系是模糊的。
- 高速时更严重：工件可能在两次曝光之间已经移出画面，或者画面里同时出现两个工件。
- `MainViewModel` 的 `_isProcessing`：上一帧没处理完就跳过。产线节拍 100ms、单帧 200ms 时，一半工件永远不会被检测，而且是**安静地漏检**——不报错、不报警、记录里少了一半件。

正确形态：相机 `TriggerMode = On`，触发一帧一检，结果跟工件 ID 走，工件流到分选位时结果刚好就绪。`ITriggerSource` 抽象是对的（注释里已预留 PlcTrigger），但 Pipeline 的"无状态单帧"模型要改成**带工件 ID 的任务流**——这是架构改动，不是加一个类的事。

### 9.3 最小可上线集（Must，缺一条就是事故）

| # | 缺口 | 为什么必须 | 工作量 |
| --- | --- | --- | --- |
| M1 | 硬触发 + 帧-工件 ID 绑定 | 没有它，检测结果无法对应到工件 | 架构级，1 周 |
| M2 | 结果输出到 PLC（OK/NG 位 + 缺陷码） | 软件只写数据库，分选机构永远不知道 | 3–5 天（NitroGateway 的 Modbus 栈可直接复用） |
| M3 | 工件计数对账 | 软件处理 N 件 vs PLC 发出 M 件，差额即漏检，必须报警 | 2 天 |
| M4 | 开机标准件校验 + NG 锁机 | 防"软件以为在工作，其实镜头松了/光源衰减了"。启动自检查的是设备存在性，**不是检测质量**，两回事 | 3 天 |
| M5 | 相机断连自动重连 | GigE 网线松了，现在 `IsAvailable=false` 后无恢复路径，产线一秒都不能停 | 2 天 |
| M6 | 配方 + 模型权重快照绑定检测记录 | 追溯要求"这批货用哪版配方、哪个权重检的"；现在配方改了，历史记录不知道 | 2 天 |
| M7 | 节拍实测 + 超预算报警 | 已有 Stopwatch/EMA FPS，但只是显示，没有阈值。YOLO 在 CPU 上可能吃掉 100ms+ | 1 天 |

M1–M7 合计约 3 周。注意 M1 是地基，M2/M3/M7 都建立在"帧有 ID"之上，所以顺序不能反。

| 缺口 | 价值 |
| --- | --- |
| 权限分级 + 参数修改留痕 | 防工人误改参数，质量体系审计要 |
| NG 率漂移监控（按天/小时趋势，超阈值报警） | 产线最贵的故障不是崩溃，是安静地失效 |

### 9.5 现实边界

一个人做不完全部——还需要真实产线、真实 PLC、机械装配、光学调试（镜头选型、光源、工作距离、景深）。所以这些不是让你这周就动工的清单。

真正的价值在面试：**能讲清"工作站和在线设备的差距在哪、我会怎么改"，比现在再多写三个检测工具值钱得多。** 因为前者证明你想过系统怎么在真实世界里活着，后者只证明你会调 API。

## 八、一句话回答"还差多少"

基建差约 4 倍工作量（约 3 天能补齐），精度体系差约 3 天且**这部分 NitroGateway 也没有、补了就是你的独占加分项**。合计 6 天左右，其中前 3 小时收益最高。

## 十、没有设备怎么验证（三圈层策略）

### 10.1 先换个问法

"没有设备"真正的意思是：**没法验证跟硬件绑定的那几件事**。所以要问的不是"怎么凑一台产线"，而是"我要验证的到底是什么假设，它的最便宜验证方式是什么"。

按验证成本分三个圈层：

| 圈层 | 内容 | 判断 |
| --- | --- | --- |
| 绿圈 | 检测算法、Pipeline、标定、坐标换算、配方系统、存储、UI、协议逻辑 | **不需要设备，现在就能验**，且你已经验了一部分 |
| 黄圈 | 触发时序、帧-工件对应、PLC 读写闭环、节拍、计数对账 | 不需要真设备，需要**仿真**；或花小钱用等价物验 |
| 红圈 | 光学成像质量、硬实时确定性、EMC/电气干扰、GR&R、机械振动 | **仿真不出来**，只能降风险 + 诚实标注为待验证 |

### 10.2 绿圈：你已经在做了，补两处

- `FileCamera`（目录 + loop + filter）+ `TestImages/VirtualCamera/{1280x1024, 2448x2048}` 已经是虚拟相机，这个思路是对的。
- 22 个单测 + 合成垫圈图回归，覆盖了标定 / 坐标 / 三个工具的算法正确性。
- 要补的：**黄金样本库**（固定 30-50 张 + 期望结果 JSON + 跑批对比）——这是把"我觉得没问题"变成"每次改动都可对比"的关键，见第五节 B1。

### 10.3 黄圈：搭一条全仿真产线（一行真硬件都不用）

这条是最有价值的答案——**M1/M2/M3/M7 的核心逻辑全部可以仿真验证**：

```
VirtualCamera(按节流出图)  ──►  Pipeline.Run  ──►  ModbusResultWriter(写 D 寄存器)
        ▲                                                      │
        │                                                      ▼
  ModbusTcpTriggerSource(读线圈/寄存器) ◄────────── 仿真 PLC(汇川 AutoShop)
```

具体六件，全部实现 `ITriggerSource` / `ICamera` / 结果输出抽象，不需要新架构：

| # | 组件 | 作用 | 说明 |
| --- | --- | --- | --- |
| 1 | 汇川 AutoShop 仿真 PLC | 提供 Modbus TCP 服务（127.0.0.1:502） | 已装。M0→线圈 0、D0→保持寄存器 0，PLC 侧零配置 |
| 2 | `ModbusTcpTriggerSource` | 实现 `ITriggerSource`，读仿真 PLC 触发位 | **真协议栈、真联调**，不是假的——这正是 JD 里"和 PLC 通讯"的实证 |
| 3 | `VirtualCamera` 节拍模式 | 按 100ms 节拍从目录顺序出图，模拟传送带 | 现有 `FileCamera` 加一个"按时间步进"选项即可 |
| 4 | 工件 ID 贯穿 | 每次触发分配自增 ID，带进 `InspectionReport` | M1 的核心：帧与工件的绑定 |
| 5 | `ModbusResultWriter` | OK/NG + 缺陷码写回 D 寄存器 | 复现 M2，且能读回来自校验 |
| 6 | 对账器 | 软件处理数 vs PLC 触发数，差额报警 | M3 的完整实现 |

跑通之后你可以说：**"触发-检测-结果回写-计数对账"这条闭环，我是在真实 Modbus 协议上联调验证过的。** 这句话比任何架构图都硬。

### 10.4 黄圈另一条：花小钱买等价物（预算 < 1000 元）

如果连仿真都觉得"不真实"，闲鱼能凑出：

| 件 | 预算 | 验什么 |
| --- | --- | --- |
| 二手海康 USB 工业相机 | 200-500 | 真 MVS SDK、真触发模式（软触发）、真帧率 |
| 24V 光电传感器 + 继电器模块 | 30-80 | 真外部触发源 |
| 二手汇川/三菱小型 PLC | 100-300 | 真 24V IO、真 Modbus 从站 |
| USB 环形补光灯 + 手机三脚架 + 手动平移台 | 100 | 真成像环境（光照、景深、工作距离） |
| **合计** | **< 1000** | 一条"伪产线"：光电触发 → 相机拍手动移动的零件 → 结果写 PLC |

只差传送带和分选机构，而这两块恰好是**纯机械**、跟软件能力无关。

**判断标准：如果验证某个假设的硬件钱 < 你半天时薪，就买；否则仿真。** 时间永远比这 1000 块贵。

### 10.5 红圈：诚实标注，不要装

这些仿真不出来，装是会被问穿的：

- **光学选型**（镜头焦距、光源角度、景深、分辨率匹配）——可以用计算降风险：每像素覆盖多少 mm、要检出 0.2mm 缺陷至少需要几个像素、景深是否覆盖零件高度差。**把计算过程写进文档，就是专业性的证明**，比假装调过强。
- **硬实时确定性**——Windows 不是实时系统，抖动 ±10ms 是常态。解法是把节拍预算写成"最坏情况"并留 30% 余量，而不是承诺精确值。
- **EMC / 电气干扰 / 隔离**——需要现场，归到部署文档里由集成方负责。
- **GR&R**——需要重复测量 10 个真实件 × 3 次，有样品才能做。面试时主动说"这是待验证项，方法论我会，缺样品"。

### 10.6 面试被问"你没设备怎么测的"

标准答法（三层，缺一层就显得空）：

> "分两类看。**算法层**我用 22 个单测加合成图回归覆盖标定、坐标、三个检测工具，还有一条端到端回归对应一个真实修过的 bug。**协议和闭环层**没有真设备，我搭了全仿真：FileCamera 当虚拟相机按节流出图，汇川 AutoShop 仿真 PLC 提供 Modbus TCP 服务，触发读取和结果回写都走真实协议栈，再加工件计数对账。**硬件相关层**——光学选型、硬触发时序、GR&R——我明确标成待验证项，光学部分我用分辨率匹配和景深计算做了预估，做法是 X。"

这个答法的杀伤力在于：大部分人要么含糊说"测过一些"，要么直接说"没测过"。**拿出仿真链路 + 明确的待验证清单 + 降风险手段**，是工程师的答法。

### 10.7 一条提醒

不要为了"能说上过产线"去凑产线。你要的是**能力证明**，不是设备。一条跑通的全仿真闭环（10.3），比一台堆在墙角吃灰的二手传送带有价值得多——因为它能被展示、能被复现、能写进简历。

**核心架构差约 3 周（硬触发 + 工件 ID 任务流 + PLC 输出），可信度机制差约 1 周，运维补丁 3–5 天。** 但最关键的一句话：现在这套是"人看着的工作站"，产线要的是"自己活着的设备"——差的不是代码量，是五个架构假设（触发源、帧-工件对应、过载处理、结果出口、失效自检），其中"取最新帧 + 处理不过来就跳过"这条，在真实产线上等于静默漏检。
