# VM 集成说明（TCP 中转，2026-10-23 定稿）

> 一句话：**VisionMaster 独立跑流程并判定，把结果用 TCP 推给本程序；本程序不加载 VM 的 SDK。**

这份文档记录了两件事：为什么放弃 SDK 进程内集成（有实证），以及现在这条链路怎么配、怎么验。

## 1. 为什么不做 SDK 集成

结论：**VM 4.2 的 SDK 上不了 .NET 8，为它加一层宿主进程的代价远超收益。**

实测证据（2026-10-23，本机 VisionMaster 4.2.0 / .NET 8）：

| 现象 | 原因 |
|---|---|
| `Error in the application.` `errorCode=0xE0000602` | 进程没有管理员权限，SDK 的 `IsServiceInstall` 调 `OpenSCManager` 拿到错误 5（拒绝访问），误判"服务未装"后尝试装服务又失败 |
| `errorCode=0xE0000600` | 服务状态校验失败（`CompareProcessIdAndPath → OpenProcess fail`），SDK 会卸载并重装 VM 服务 |
| .NET 8 进程直接崩溃 `0xC000000D`，`E0000603` | `VM.Core.dll` 目标是 `.NETFramework v4.6.1`，内部依赖 `System.Runtime.Remoting`（.NET 5+ 已移除） |

**逐条排除过的（别再重复试）**：`.sol` 路径与文件名、App.config 的 `StartServerByExe`/`ServerPath`、
DLL 是否拷全、`Librarys.Config`/`WinIo64.sys` 等非 DLL 依赖、目录结构平铺、
`<probing privatePath>`、服务是否在运行、VM 授权（`Monitor.log` 里授权有效，限 4 台相机）。

**net48 环境下确实能跑通**（实测 `LOAD OK` / 流程找到 / 喂图 `Run` 成功 55ms），
但那要求：以管理员身份运行 + 完整抄 VM 客户端的 config + 依赖 VM 的安装目录结构。
把它包成"net48 宿主进程 + 命名管道"在当前规模下不划算。

### 业界怎么做的（查证，不是猜）

两种做法都真实存在：

- **VM 独立运行 + 通信**：海康 V 社区给的方案排序里，这条是第一推荐（解耦、稳定、符合现场规范）；
  VM 里拖一个「发送数据」模块绑结果端子就能发，几乎不写通信代码。
- **上位机进程内集成 SDK**：有人明确在用，理由是延迟低、界面统一；但同一批文章都写道
  「环境依赖更敏感，DLL 路径、运行时目录、授权信息都要放好，稍有不慎就初始化失败」，
  而且**上位机一律是 .NET Framework 4.6.1–4.8**。没人用 .NET 8 当宿主。

所以本程序选了第一条：**保住 .NET 8，把判定交给 VM，只收结果。**

## 2. 现在的链路

```
┌─────────────────────────────┐        ┌──────────────────────────────────┐
│ VisionMaster（独立进程）     │        │ VisionStation（.NET 8，普通权限）  │
│                             │        │                                  │
│ 相机采集 → 流程1             │        │  VmResultListener                 │
│   快速匹配 → 位置修正        │  TCP   │   ├─ VmResultParser  (JSON→报告)  │
│   → 圆查找（公差在 VM 里配） │ ─────► │   ├─ InspectionWorkflow.Accept... │
│                             │ 一行   │   │    读图 + 标注 + 存库          │
│ 判定 IsRunOK = 唯一真相源    │ JSON   │   └─ 广播界面 + 回 PLC            │
│ 发送数据模块（TCP 客户端）   │        │                                  │
└─────────────────────────────┘        └──────────────────────────────────┘
```

**方向为什么是 VM 做客户端**：VM 的「发送数据」配成 TCP 客户端只需要填 IP 和端口；
反过来要在 VM 里配服务端并处理并发，配置更绕、收益一样。

**相机归 VM。** 同一台相机不能被两个进程同时占用，这是 GigE 独占语义决定的，不是设计选择。
所以本程序干脆没有采图能力：2026-10-26（提交 `f6d0239`）相机层整体删除，`VisionStation.Devices`
下只剩 `Device` / `Plc` / `Trigger` / `Vm` 四个目录。要离线验图，用 `tools/VmSimulator` 推报文，
并在报文里带上图像路径（`--image "D:\img\1.bmp"`）—— 走的和真实 VM 完全同一条路径。

### 3.1 搭流程

1. 图像源：接相机（产线）或「本地图像」（离线调试）
2. 检测链：快速匹配 → 位置修正 → 圆查找 / 测量 / 缺陷检测

### 3.2 配通信设备 + 加「发送数据」模块

**关键认知（2026-10-23 实测 UI）**：4.2 的「发送数据」模块里**没有地方填 IP 和端口**。
它只选「发给谁」——`输出至` 有五个选项：`数据队列` / `通信设备` / `全局变量` / `视觉控制器` / `发送事件`。
TCP 地址要到**通信管理**里配，发送数据只是引用那个设备。所以顺序不能反。

**第一步：建通信设备**

主界面菜单 **系统 → 通信管理**（工具栏也有同名图标）→ 添加通信设备：

| 项 | 值 |
|---|---|
| 设备类型 | **TCP 客户端**（VM 主动连上位机，上位机做服务端） |
| 目标 IP | 上位机 IP，同机就 `127.0.0.1` |
| 目标端口 | `9100`（与 appsettings 的 `VmLink:Port` 一致） |

**第二步：发送数据模块**

流程末尾放 **发送数据**，双击：

| 项 | 值 |
|---|---|
| 输出配置 → 输出至 | **通信设备**（默认是"数据队列"，不改会什么都不发出去） |
| 输出数据 → 选择队列 | 这时变成选设备，选中刚建的 TCP 客户端 |
| 选择数据 | 点右侧链子图标，订阅要发出去的那一项 |

### 3.2.1 发 JSON 还是发分隔符？（2026-10-23 实测结论：别用格式化拼 JSON）

想在 VM 4.2 里拼一行 JSON，唯一能放文本的是「格式化」模块，但**这条路实测走不通**：
把 JSON 文本粘进去点保存，报 **「格式化验证失败！」**（VM 自己的提示串是 `Lang_FmtTestFail`）。
原因在模块设计上 —— 它的每一行本质是"一条订阅项"，纯文本没有绑定路径过不了校验，
而且 `{ }` 还会被当成占位符语法。**别在这上面耗时间。**

改走 VM 原生的分隔符格式，接收端已经支持（`VmResultParser.ParseDelimited`）：

| 位置 | 怎么配 |
|---|---|
| 发送数据1 | 订阅 `圆查找1` 的判定输出（`IsRunOK` / 模块状态） |
| 发送数据2 | 订阅 `圆查找1` 的 `Radius` |
| 分隔符 | **打开**，值填 `;` |
| 结束符 | **打开**，值 `\n` |

发出来就是一行：`OK;12.345`

接收端这样解释：**第 1 段是总判定**（接受 `OK/NG/PASS/FAIL/1/0/TRUE/FALSE`），
后面按顺序对应配方 `vm.outputs` 的顺序 —— 所以第 2 段自动落成"外径"、单位取映射里的 `px`。
这种格式没有逐项判定，各项沿用总判定（不替 VM 造逐项结论）。

> 要发真正的 JSON，只有一条路：VM 的**全局脚本**里用 C# 调 `SendCommDeviceData(data, deviceID)`
> 自己拼字符串。示例方案 `OCRDemo.sol` / `DeepLearningDemo.sol` 里都带 `GlobalScript`，可以参考。
> 现阶段没必要，先用分隔符把链路跑通。

**它发的是「订阅进来的值拼接成的字符串」**，不是我们自定义的格式。
所以要想发一行 JSON，得让订阅源本身就是一行 JSON 字符串 —— 用 **格式化** 模块拼好再订阅：

```
格式化1（输出一行 JSON 文本）→ 发送数据（输出至 通信设备）
```

```json
{"verdict":"OK","imagePath":"D:\\temp\\vm.bmp","items":[{"label":"外径","value":0.0,"unit":"px","ok":true}]}
```

里面的数值/状态用格式化的「插入变量」换成 `圆查找1` 的输出。**先别急着拼全**：
第一步只要能发出一条固定字符串 `{"verdict":"OK"}`，管道就算通了，再逐项换变量。

发送数据**不保证带换行**（VM 侧没有结束符设置）。接收端按行定界，所以：
VM 每次发完若关闭连接，收端在连接结束时会拿到最后一段（已实测可行）；
若一直保持连接且不带换行，就会一直攒着不触发 —— 这种情况要么改用「发送事件」，
要么在格式串末尾加换行，实测结果见 5.1 抓包。

### 3.3 存方案

存成 `.sol`（当前配方指向 `Config/solutions/washer-2448.sol`）。

### 3.2.2 最省事的做法：用全局脚本发（推荐，不用点订阅）

VM 的「发送数据」要一行行点链子订阅，慢且容易点错。**全局脚本里一行就够了**。
脚本源码放在 `docs/vm/全局脚本-发送结果.cs`，整段粘进 VM 的全局脚本编辑器即可。

```csharp
SendCommDeviceData("OK;" + _count + "\r\n", 1, 0, DataType.StringType);
```

| 参数 | 含义 |
|---|---|
| 第 1 个 | 要发出去的字符串。**末尾 `\r\n` 必须自己加** —— 接收端按行定界，没换行会一直攒着 |
| 第 2 个 | 通信设备编号，就是「通信管理」设备列表里的序号（第 1 个 = 1） |
| 第 3 个 | 子地址（PLC/Modbus 用，TCP 直连填 0） |
| 第 4 个 | `DataType.StringType`（还有 IntType / FloatType / ByteType） |

脚本里可用的基类方法（从安装目录的 DLL 里核对过，不是猜的）：
`InitSDK` / `StartGlobalCommunicate` / `SetScriptContinuousExecuteInterval` /
`SendCommDeviceData` / `ConsoleWrite` / `ExecuteProcessOnce` / `GetGlobalVariable*Value`。

> 这一步发的是 `OK;1`、`OK;2`…（计数器），用来证明"脚本 → TCP → 上位机"这条线通。
> 通之后再换成真实数值：要么回到「发送数据」订阅模块状态，要么在脚本的
> `ResultDataCallBack` 里按模块 ID 取 `Radius`（需要 Marshal 结果结构体，成本更高）。

## 3.3 实测踩坑清单（2026-10-25 第一次真机对接，逐条都是踩出来的）

| 现象 | 真实原因 | 处置 |
|---|---|---|
| 图像源找不到"选文件夹" | VM 4.2 的「图像源」只有 `本地图像` / `相机` 两种类型（`Module(sp)/x64/Collection/ImageSourceModule/ImageSourceModuleAlgorithmTab.xml` 的枚举） | 路径只能填**一个文件** |
| 只指了一张图，标题却显示 `(1/47)` | `AutoPlay=True` 会**自动枚举同目录下全部图片**并按序号往下走（`InitialSN` 是起始序号，`Interval` 是间隔） | 批量喂图不用改名，把那 N 张放同一目录即可 |
| 配好了却一条数据都没发出去 | 「发送数据」的 `输出至` 默认是**数据队列** | 改成 **通信设备**，再选具体设备 |
| 报 `E0000314 未找到订阅结果值` | 订阅的是某个模块的输出，但那个模块**这一轮没有产出**（上游是红的/没执行）。不是发送模块的问题 | 先把上游模块弄绿，别在发送数据里找原因 |
| 报 `E0000105 连接失败` | 9100 端口**没人监听**（上位机没启动） | 先起上位机（它是服务端），再回 VM 点运行 |
| 界面上一串 0/1，标签却是「外径、值2、值3…」 | 分隔符报文只带值不带名，值按配方 `vm.outputs` 的顺序落位；映射不够长就退化成「值N」 | 改 `vm.outputs` 使其条数与顺序和订阅一致 |
| 五个 ROI 想汇总成一个总判定 | 直接拿某一个 BLOB 的模块状态当判定 → 漏检（其余 4 个缺件照样报 OK） | 用 **逻辑（`AndModule`）** 选「与」，输入订阅 5 个模块状态，输出 **BOOL** 当报文第 1 段 |

三条与判定有关的硬事实：

- **模块状态是 0/1/2**：`1` = OK，`0` = 未判定/未执行，`2` = NG。上位机这侧 `0` 和 `2` 都当 NG（`VmResultParser.ParseVerdict`）。
- **第 1 段必须是判定**。分隔符格式里如果第 1 段是面积、分数这类数值，会被当判定解析，整帧就乱了。
- **「条件检测」能写表达式但容易卡**（语法/变量名都要对）；纯下拉的「逻辑」模块更适合汇总。

## 3.3.1 让 VM 把图送到上位机（2026-10-26 补）

**图永远不走报文，走文件系统。** 报文里只放**路径字符串**，上位机按路径读图显示/标注/入库。

链路：

```
VM 流程末尾加「输出图像」模块 → 图落到磁盘
    ↓
「发送数据」把这个模块的路径输出也订阅成一段（或全局脚本里拼进 JSON 的 imagePath）
    ↓
上位机 VmResultParser 认出这一段是路径 → report.ImagePath
    ↓
InspectionWorkflow 读图 → MatBitmap 转 BitmapSource → 上屏 + 画标注
```

**分隔符格式怎么带图**（最省事，不用写脚本）：
报文变成 `OK;1;1;1;1;1;D:\VMOut\20261026_134118.bmp`。
解析器按「有路径分隔符 **且** 扩展名是 `.bmp/.jpg/.jpeg/.png/.tif/.tiff`」识别，
**识别出的这一段不占 `vm.outputs` 的位置** —— 它后面的数值映射会自动往前挪一格，
所以配方不用改。规则在 `VmResultParser.LooksLikeImagePath`，4 条单测钉着。

**三个必须注意的点**：

1. **路径要是绝对路径**。相对路径会按 exe 所在目录解析，现场一定找不到。
2. **文件名必须每件不同**。固定一个 `latest.bmp` 会让所有历史记录指向同一个文件，
   下一件一来图就覆盖 —— 历史页里全是"死链"，追溯等于没有。「输出图像」模块如果有
   时间/序号命名（或时间子目录）就用它；没有就加个脚本模块动态改路径
   （`CurrentProcess.GetModule("输出图像1").SetValue("OriginImgPath", ...)`）。
3. **上位机不存图**（`AcceptExternalCoreAsync` 故意不落盘）：VM 存过一份，再存一份就是
   两份真相，且 2448×2048 一张约 5MB，一年按百件/分算能吃掉几十 TB。保留期清理的
   前提是文件名里带日期/结果，否则上位机不敢删别人的文件。
   2026-10-27 起，配套的 `ImageStoreService` 与 `Storage:Mode` **已整体删除**
   （连同 7 条单测、`StorageLayerTests` 里 4 条用例、`CameraFrame` 类型）——
   它们没有生产调用者，留着只会让人以为存图策略还在生效。
   只剩 `Storage:ImageFolder` 保留：它不是"往哪存图"，而是后台管家**清哪个目录**；
   想让它真正管到 VM 的图，就把这项指到平台存图目录（指哪儿清哪儿，代码不做猜测）。

| 现象 | 原因 | 处置 |
|---|---|---|
| 界面黑屏，提示"未发 imagePath" | 报文里没有路径段 | 见本节：加「输出图像」+ 订阅路径输出 |
| 提示"路径不存在" | 相对路径 / VM 存到别的机器 / 存图没使能 | 用绝对路径；确认 `输出图像` 的保存使能勾上 |
| 提示"无法解码" | 文件大小为 0 或格式是 VM 私有 raw | 存图格式选 bmp/jpg/png |
| 历史页每一条点开都是同一张图 | 存图用了固定文件名 | 换成时间/SN 命名 |

## 4. 上位机侧怎么配

`appsettings.json`：

```json
"VmLink": {
  "Enabled": true,
  "Port": 9100,
  "BindAddress": "127.0.0.1"
}
```

配方（`.active` 指向的那份）里：

```json
"engine": "Vm"
```

启动后日志会出现：

```
[VM链路] 已启动，监听 127.0.0.1:9100，等待 VisionMaster 推送
```

> `VmLink:Enabled=true` 但配方引擎不是 `Vm` 时**不会**启动监听，启动日志里会给一条警告。
> 端口被占用会直接让启动失败 —— "起了但没在听"比启动失败难查得多。

## 5. 怎么验（不需要 VM 客户端）

```bash
dotnet run --project tools/VmSimulator
dotnet run --project tools/VmSimulator -- --count 5 --interval 1000 --verdict NG
dotnet run --project tools/VmSimulator -- --raw '{"verdict":"OK"}'
# 带图：报文里塞 imagePath，界面才走"读图 + 标注"那条路径（原先用 File 相机做的事）
dotnet run --project tools/VmSimulator -- --image "D:\img\1.bmp"
```

发完之后去检测页看结果、去历史页看记录。用 `--raw` 发畸形数据可以验证"解析失败也入库为 NG"这条路径。

### 5.1 第一次接真实 VM：先抓包，再改格式

模拟器发的是"我以为 VM 会发的东西"。真实 VM 发什么，得先看一眼 —— 否则格式串对不上时，
界面上的表现只是"没反应"，查不出问题在哪。

```bash
# 先关掉 VisionStation（它占着 9100），然后用抓包模式占住端口
dotnet run --project tools/VmSimulator -- --listen --port 9100 --timeout 120
```

在 VM 里手动跑一次流程（末尾挂着发送数据模块），终端会为每段数据打印两行：

```
--- 第 1 段，218 字节 ---
  文本：{"verdict":"OK", ...}
  转义：{"verdict":"OK", ...}\n
```

**转义那行才是重点**：能看出结束符是 `\n` 还是 `\r\n`、末尾有没有 `\0`、
中文是 UTF-8 还是 GBK（GBK 会显示成 `\xC4\xE3` 这种）。

对照结果处理：

| 看到的现象 | 含义 | 怎么办 |
|---|---|---|
| 一段就是完整 JSON，`\n` 结尾 | 和接收端约定一致 | 直接用，不用改代码 |
| 一次连接里来了好几段 | VM 按字段逐条发，不是一个格式串 | 先把格式串合成一条；合不了告诉我，我在解析器里做多行拼装 |
| 中文变成 `\xC4\xE3` 这类 | 发的是 GBK | 我在解析器里加 GB18030 兜底 |
| 一段都没收到 | 模块没被执行或地址端口不对 | 检查模块是否连在流程里、是否被条件模块跳过、地址是不是 `tcp://127.0.0.1:9100` |

## 6. 判定语义（这部分和以前一致，故意的）

1. **判定权归 VisionMaster。** 每一项的 OK/NG 取 VM 给的值，上位机不重算公差。
2. **没有判定的结果不能算合格。** `ok` 字段缺失按 NG；既无 items 也无 verdict 时整帧 NG。
3. **空结果集判 NG。** 一条结论都没有的检测不能算通过。
4. **解析失败也入库。** 非法 JSON 会带原文片段入一条 NG 记录，不会静默丢帧。
