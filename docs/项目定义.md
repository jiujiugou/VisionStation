## 1. 这是什么类别

**视觉检测工站上位机**（Vision Inspection Station Host）。

业界对这类软件的常见叫法：检测站软件、CCD 检测上位机、工站主控。它不是一个新品类，是一个存在很久、有成熟做法的品类。

**一句话定义：判定归平台，工位归它。它不管怎么判，只管这一件判完之后的所有事。**

**它不是什么**（这几条决定方向，写在这里是为了防止定位漂移）：

| 不是 | 那是谁 | 为什么不做 |
|---|---|---|
| 视觉算法平台 | VisionMaster / Halcon / VisionPro | 平台的核心资产是算法库和流程编辑器，单个项目做不过；做了也不如"把链路接扎实"值钱 |
| MES / 车间系统 | MES、SCADA、组态王 | 车间级管多工位、排产、报表；工位级的价值恰恰是**离线自治** |
| 相机 SDK 封装库 | 厂商 SDK | 只封装 SDK 没有界面、没有记录、没有 PLC 交互，等于半个驱动 |
| 组态软件的视觉插件 | 组态软件 | 组态做图像 + 判定 + 追溯这一套不顺手，是特定形态而非通用组态 |

判据只有一条：**这个功能是否让"这一台工位"更好用。** 让"视觉算法更强"的，不做。

## 2. 四层归位

```
┌────────────────────────────────────────────────────┐
│ 车间层   MES / SCADA / 数据库                       │  多工位汇总、报表、排产
├────────────────────────────────────────────────────┤
│ 工位层   VisionStation            ← 我们在这        │  状态机、联锁、结果落账、界面、追溯、报警
├────────────────────────────────────────────────────┤
│ 平台层   VisionMaster                               │  算法、流程、判定权、公差、标定
├────────────────────────────────────────────────────┤
│ 设备层   相机 / 光源 / PLC / 气缸                    │  采图、执行
└────────────────────────────────────────────────────┘
```

| 层 | 管什么 | 不管什么 |
|---|---|---|
| 车间层 | 多工位汇总、排产、对外报表 | 单个工位的实时状态与操作 |
| **工位层（本程序）** | 工位状态机、启动联锁、结果落账与追溯、操作员界面、报警、与 PLC 交互 | 怎么判、怎么标定、怎么调算法参数 |
| 平台层 | 图像源、定位、测量、缺陷、**公差与判定**、流程调试 | 进数据库、管操作员、直连产线 PLC |
| 设备层 | 采图、动作执行 | 判定、记录 |

**边界为什么这么切**：同一台相机不能被两个进程同时占用（GigE 独占语义），所以"谁采图"必须只有一个答案。答案是平台——它同时掌握算法与判定权，把图留给它，两边都不用同步状态。

**这个切法的代价**（诚实记录）：上位机拿不到内存里的 `Mat`，只能拿"平台存下的图文件"。所以图像的时效性受磁盘 IO 约束，做不到零延迟——这是选择，不是缺陷。

## 3. 业界标配的功能集

选两个真实参照物，都是"成型的东西"：

**参照物 A：商用产品**。奥鲲《机器视觉分拣调度上位机》的功能划分
（[aukundev.com](https://aukundev.com/uppercompter/250.html)）：视觉结果监控与识别框叠加、KPI 看板（工单进度/节拍/产量/良品率）、可视化规则编排、多设备协同、配方管理、多维报表、**历史追溯（把检测图片、识别结果和最终去向关联）**、导出 Excel/PDF、对接 MES、统一设备管理（相机参数、PLC 寄存器映射）。

**参照物 B：开源同名项目**。GitHub `agentthink/vision-station`
（[github.com](https://github.com/agentthink/vision-station)）：WPF 工站上位机，集成 PLC 通讯、相机检测、**启动联锁**、自动工步、**NG 踢废并确认**、配方管理、报警日志、生产追溯；工步为「等待到位 → 读条码 → 触发相机 → 等待结果 → OK 放行 / NG 踢废并确认 → 写追溯」；50ms 独立扫描线程，界面只拉快照；默认带仿真 PLC 与仿真相机。

把两者的功能并集当作"业界标配"，对照本项目现状：

| # | 能力 | 业界标配 | VisionStation 现状 |
|---|---|---|---|
| 1 | 工位状态机（空闲/自动/暂停/急停/故障） | ✅ | ✅ 有：启动/停止/自动/手动/急停（`ControlPanelViewModel`） |
| 2 | **启动联锁**（条件不齐不许启） | ✅ | ❌ **缺**：只有上电自检 5 项，启动前不校验"平台已连接 / 配方已加载 / 无未复位故障 / PLC 健康" |
| 3 | 触发（到位信号 → 拍照） | ✅ | ⚠️ 有：手动 / 定时 / PLC 上升沿（`ITriggerSource`），但 **PLC 上升沿只握手、不驱动检测**，见 §7.4 |
| 4 | **NG 处置闭环**（执行机构动作 + 到位确认） | ✅ | ❌ **缺**：只把 OK/NG 写回 PLC 寄存器，不确认执行机构是否动作到位 |
| 5 | 条码 / SN 绑定 | ✅ | ⚠️ 报文层能收到 `Sn`（`VmResultMessage.cs:69`），但**通路未建**：`VmResultParser` 不往下传，`InspectionReport` 与 `InspectionRecord` 都没有该字段，历史页无法按 SN 检索；本程序不读码、不校验重复 |
| 6 | 配方管理（换型） | ✅ | ⚠️ 有配方文件与引擎选择，**但顶栏只显示不切换**（`TopBarViewModel.cs:22` 明写"不提供下拉切换"） |
| 7 | **结果追溯**（图 + 值 + 去向） | ✅ | ✅ 有：历史页（时间/判定/引擎筛选 + 点开看当时的图与逐项结论） |
| 8 | KPI（产量 / 良率 / 节拍） | ✅ | ✅ 有：**今日**口径，启动时从库补基数，重启不归零 |
| 9 | 报警与日志 | ✅ | ✅ 有：Serilog 文件日志 + 界面日志面板 + 状态栏 |
| 10 | 权限分级 | ✅ | ✅ 有：四级角色（`UserRole.cs:14`）+ 12 个权限位（`:36`）+ 按需登录 + 超时降级。**但真正被 `HasPermission` 拦过的只有 `ViewHistory` / `ViewAudit` / `EnterEngineerMode` 三个**；`RolePermissions.RequiresPermission` 没有生产调用者，`CameraSettings` 已无消费者——12 个位不等于 12 道闸 |
| 11 | 仿真联调（假 PLC / 假平台） | ✅ | ✅ 有：`VmSimulator`（假 VM，按节拍推报文）、`scripts/rtu_slave.py`（Modbus RTU 从站 + 汇川 ST 逻辑，D100–D106 全套）、`tools/ClosureProbe`（跑真实组合根并注入 8 种产线意外）；只缺 Modbus **TCP** 从站 |
| 12 | 设备统一管理（图像源 / 寄存器映射） | ✅ | ⚠️ 图像源目录在「图像来源」页配（仅工程师模式），PLC 地址在 `appsettings` 里配，没有集中管理界面 |
| 13 | **通讯健康监控**（链路/设备存活可见） | ✅ | ✅ 有：VM 链路四态（未监听 / 未连接 / 正常 / 断流），每秒检查、只在状态翻面时广播；断流告警区分停机与故障；状态栏「平台」灯常驻 |

**一句话结论：明确缺的只剩 2 项（2 启动联锁 / 4 NG 处置闭环），另有 6/12 两项是半成品；
多出来的全是工程基建。**
本项目在测试、离线验证工装这几项上超过多数同类（权限位划分得细，但实际拦截的只有三个，不算优势）；在联锁与 NG 闭环这两项上落后。

> **2026-10-24 当天的两次变化**：
> ① 第 13 项（通讯健康）补齐——原先"平台崩了"与"产线没料"在界面上是同一个黑屏，这是漏检级风险；
> ② 第 7、8 项（追溯出口、良率口径）补齐——数据在库里躺了 30 天没有出口，良率是内存计数、重启归零。
> 现在历史页能按时间/判定/引擎筛，点开看当时那张图和逐项结论；良率是"今日"口径，启动从库补基数。

### 4.2 半成品（有骨架，闭环没合上）

| 项 | 缺的最后一环 |
|---|---|
| 配方管理 | 有两份配方文件（`default.json` / `default-2448.json`）、有 `SwitchRecipe` 权限位，**但没有切换入口**；换型只能改 `appsettings` 重启。见 §5 P2-1——不是加个下拉就完事 |

| 不做 | 原因 |
|---|---|
| 视觉算法 / ROI 编辑器 / 标定向导 | 归平台。自研算法工具链已于 2026-10-23 删除（净 −4479 行），不要再回来 |

| **离线跑批 / 黄金样本基线** | **已删除（2026-10-27）**：工具与数据集一并删除，因为运行时从来只跑 VM，离线跑批没有使用者。原来那份检出率基线随之失效、不再可复现，不要再引用 |
| 模型训练 / 标注工具 | 连推理都不在仓库里了，训练更不该在这里 |
| MES / ERP 对接、云端同步 | 单机离线是定位前提；一旦联网，断网降级、数据补传、安全认证全要重做 |
| 多相机多工位 | 是另一个产品形态（车间级），不是本程序的扩展 |
| 视频流式预览 | 见 §7.2：产线不需要，代价极高 |

## 5. 缺口优先级

排序依据：**出事后果 × 补齐成本**。安全项优先于功能项，功能项优先于体验项。

### P0 —— 不补会真出事

| # | 做什么 | 为什么是 P0 | 成本 |
|---|---|---|---|
| 1 | 启动联锁 | 条件不齐允许启动 = 带病运行 | 一天（6 个条件，参考参照物 B） |

### P1 —— 业界标配而我们缺

| # | 做什么 | 依据 | 成本 |
|---|---|---|---|
| 1 | NG 处置闭环（若工位有踢废气缸） | 对照表 #4 | 一天（需现场硬件；无硬件则明确记为"该工位不踢废"，不再挂在账上） |
| 2 | **触发链路二选一**：按引擎分流触发源，或明确写"本程序不参与触发" | §7.4：现在是"代码上像在触发、实际不检测"的中间态，最伤可维护性 | 半天（选"承认现状"只改文档与提示文案） |

### P2 —— 体验与完善

| # | 做什么 | 备注 |
|---|---|---|
| 1 | 配方切换入口（顶栏下拉或配方页） | **不是加个下拉就完事**：`RecipeConfig`、`IInspectionEngine`、`VmInspectionDriver` 的输出映射三者都是单例且持有旧配方引用。要能换，得先加一层「可换配方/引擎」的包装（照 `SwappableCamera` 的做法），并规定"运行中不准切换"。属于架构改动，单独一轮做 |
| 2 | 上屏降采样（1280 宽） | **已完成（2026-10-24）**。单帧内存拷贝从 30MB 降到 7.5MB；实际收益还没压测，`VmSimulator --interval 200` 打一次看 `耗时:{Ms}ms` 即知 |
| 3 | 触发来源记真实值 | **已完成（2026-10-24），但 2026-10-26 相机删除后已无实际意义**：`RunOnceAsync` 恒返回 null，生产上入库的 `TriggerSource` 只剩 `VM`；Manual / Timer / PLC 是相机层还在时的历史取值，`TriggerOrigin` 现在只剩代码与单测 |
| 4 | 图像区 NG 回看 | **已完成（2026-10-24）**。做成"留最近一张、可切回"而不是"钉住不换"——停在历史帧上的监视器比黑屏更危险 |

**不做清单**：属于 §4.3 的任何一项，无论看起来多有趣。

## 6. 三类使用者

| 角色 | 在工位上做什么 | 只关心 |
|---|---|---|
| **操作员** | 上班开软件、看判定、卡住时复位、急停 | 现在能不能检、刚才那件 OK 还是 NG、为什么不动了 |
| **视觉调试工程师（本岗位）** | **在 VisionMaster 里**搭流程、标模板、调公差；**在本程序里**验链路、查某件为什么 NG | 平台与本程序有没有接上、这个结果是不是平台给的、这条 NG 的数值是多少 |
| **设备维护 / 工艺** | 看良率、导出记录、清磁盘、查掉线与重启原因 | 这批合格率多少、记录和图片还在不在、昨晚为什么重启过 |

界面的取舍由此决定：**默认落在「检测」页（操作员视角）**；「图像来源」页只在工程师模式下可见；历史页操作员也能进；审计页只对管理员可见（`SidebarViewModel` 的可见性由"模式 + 权限位"两个维度共同决定）。

侧边栏共四个页面：**检测 / 图像来源 / 历史 / 审计**（`NavigationService.cs:12-15`，上半是检测，下半三个按权限出现）。**没有实现的入口一个都不摆**——宁可空着，也不给操作员一个点了没反应的假按钮。

## 7. 检测链路

**只有一条**：平台采图、平台判定、把结果推过来。

原来的"自动模式（本程序采图 → 引擎判定）"随相机层一起删除（2026-10-26）。
`InspectionWorkflow.RunOnceAsync` 现在**永远返回 null 且不入库**——保留这个方法，只是为了让触发链路和界面上那个按钮有个落点，不至于点下去毫无反应。

### 7.1 主链路（平台采图、平台判定）

```
VisionMaster 独立跑流程 → 「发送数据」经 TCP 推一行结果 → VmResultListener(:9100)
 → VmResultParser 解析 → InspectionWorkflow.AcceptExternalAsync
 → 按报文路径读平台存的图 → 标注 → 降采样上屏 → 入库 → 回 PLC(D101)
```

关键边界：**不采图、不存图、不重新判定**。相机归平台（GigE 独占），图片归平台（本程序只读），判定权归平台（C# 不留第二份公差）。

`IPushDrivenEngine` 让自动循环跳过主动检测，否则每 2 秒产生一条假 NG 污染良率统计。

**链路活着吗**：`VmInspectionDriver` 每秒比对一次（`VmLinkMonitor.Evaluate`），四态为
未监听 / 未连接 / 正常 / 断流。判定基准是 `最后一条结果时间 ?? 本轮连接建立时间`——
后者兜住"刚重连还没来第一件"的情况，否则每次重连都会误报一次。
断流时运行中记 Error、停机只记 Info：产线一停就刷告警的话，操作员会学会无视它。

### 7.2 为什么不做视频流

| 方案 | 能否用 | 结论 |
|---|---|---|
| 平台 SDK 直接拿 `Mat` | ❌ | VM 4.2 SDK 是 net461 + Remoting，.NET 8 加载即崩（三个错误码已实证） |
| 平台存图 + 上位机读文件 | ✅ | **当前做法**，任何 .NET 版本可用，跨机器也行 |
| 平台自带的运行界面（F10） | ✅ | 能用，但那样就不需要上位机了 |
| `SetParent` 把平台窗口塞进来 | ⚠️ | 跨进程，焦点/DPI/关闭顺序都是坑，产线不用 |

**是"每件一张结果图"，不是"实时视频流"**。产线上没人把平台的实时画面流式推到上位机：带宽、延迟都不划算，而且操作员要看的不是动画，是"这一件判了什么"。

### 7.3 高节拍下的边界

单帧开销链（`AcceptExternalCoreAsync`）：`Cv2.ImRead` 全分辨率解码 → 两次 `MatBitmap.ToBitmapSource`（原图 + 标注图）→ 一次 SQLite 写入。

`MatBitmap.ToBitmapSource`（`MatBitmap.cs`）做的是 `new byte[stride*height]` + `Marshal.Copy` + `BitmapSource.Create`，**全量拷贝**；未降采样时 2448×2048 每帧内存进出约 45–60MB，全部落在大对象堆。

**结论**：CPU 可支撑 5 件/秒，但内存分配速率与人眼分辨力才是上限。
**因此界面不追每一件**：OK 只更新数字，NG 换图并保持 2 秒（窗内到达的 OK 不抢画面，但照常入库回写）。

**2026-10-24 已实施降采样**：`MatBitmap.ToBitmapSource(mat, maxWidth)` 在通道归一之后
按 `InterpolationFlags.Area` 缩到 1280 宽。单帧两次转换的内存拷贝从 30MB 降到 7.5MB。
注意顺序：**标注必须画在原尺寸上**（`DrawRect`/`DrawCircle` 的坐标是绝对像素），画完再缩。
实际收益还没压测——用 `tools/VmSimulator --count 50 --interval 200` 打 5 件/秒，
看日志里的 `耗时:{Ms}ms` 分布再决定要不要继续优化。

### 7.4 半假触发：D100 不驱动检测（当前缺口）

真实产线上，PLC 置 D100 → 平台拍照判定 → 推结果 → 上位机回写 D101，是一条链。
本程序里这条链缺了中间一段：

```
PLC 置 D100=1
 → PlcTriggerSource 读到上升沿 → 清 D100、心跳照发 ✅
 → InspectionPageViewModel.RunFrameAsync → InspectionWorkflow.RunOnceAsync
 → 立刻 return null（VM 是 IPushDrivenEngine，主动检测被跳过）❌ 检测没跑
```

也就是说，**D100 现在的作用只有握手和计数（D106），不影响 D101**；D101 只随 VM 推来的帧变化。

为什么一直没修：两种修法都不便宜——
- **按引擎分流触发源**：VM 模式下干脆不轮询 D100，改由 VM 自己收触发；要动 `ITriggerSource` 的选择逻辑与配方语义；
- **承认现状**：文档写清"本程序不参与触发"，D100 只剩心跳与计数价值。

现状是"代码上像在触发、实际不检测"，这是最不该留的中间态。**待拍板。**

## 8. 核心概念

| 概念 | 含义 | 落在哪 |
|---|---|---|
| **配方（Recipe）** | 一份作业指导书：画面尺寸 + 引擎选择 + 引擎参数。换产品 = 换配方 | `Config/recipes/*.json` |
| **引擎（Engine）** | 判定逻辑的归属。只有 `Vm` = 平台流程；`Onnx` 已于 2026-10-27 整体删除，不再有第二条路线 | `Engines.Vm`，由配方 `engine` 选择 |
| **结果项** | 报告里的一条结论：业务名 + 是否合格 + 指标 + 角色 | `InspectionReport.Results` |
| **判定语义** | 所有结果项都 OK 才算 OK；**结果为空必须判 NG**——一项都没跑不代表合格 | `InspectionReport.IsOk` |
| **ROI / 标定** | **均归平台**（`.sol` 里画、平台里标）。本程序不提供编辑，也不维护 px/mm | `.sol` |
| **在途工作** | 关闭窗口时还在跑的检测帧，必须等它收尾或超时才退出 | `InFlightWorkMonitor` |

## 9. 判定"做完"的标准

不按代码行数、不按功能列表，按**能不能回答这些问题**：

1. 换一个零件，能不能不动代码？（部分能：改配方文件的 `vm.outputs` 与对应 `.sol`；**切换入口是欠账**，且运行时不支持换引擎）
2. 一件被判 NG，能不能说清是哪个模块、什么数值、超了多少？（能）
3. 保留期内的任意一件，能不能查到当时的结论和那张图？（**能**：历史页按时间/判定/引擎筛，点开看当时的图与逐项结论）
4. 平台挂了、网线掉了，操作员能不能在屏幕上看出来？（**能**：链路四态 + "已 N 秒没有结果"，运行中断流报 Error）
5. 条件不齐（平台没连上、配方没加载、故障没复位）时，能不能拦住启动？（**不能——P0**）
6. 软件连续跑一周，会不会内存涨、磁盘满、崩了没人管？（有管家与看门狗兜底）
7. 改了 VM 流程，是变好还是变坏，有没有数字说话？（**不能**：原来的黄金样本库与离线跑批已随 ONNX 于 2026-10-27 一并删除，目前没有回归基线）
8. 关窗口时正在检测的那一帧会不会被撕掉？（不会）

**当前 8 条里：5 条完全成立（2/3/4/6/8），1 条部分成立（第 1 条缺配方切换入口），
2 条不成立（第 5 条无启动联锁、第 7 条没有回归基线）。第 5 条就是 §5 里 P0 的来源——这个顺序不是拍脑袋排的，是从这张清单倒推出来的。**

> 2026-10-24：第 3、4 条当天从"不能"变成"能"。这份清单的价值就在这——
> **每条都是可以被事情推翻的断言，而不是永久的自夸或永久的自责。**
