# VisionStation 项目定义

> 本文回答一个问题：**这个软件是什么、给谁用、做到哪儿算做完。**
> 不写怎么实现（看 `README.md` 与代码），也不写 WPF 怎么写（看 `docs/WPF开发规范.md`）。
>
> 最后核对：2026-10-20，对照当前 `src/` 代码与 `appsettings.json`。

---

## 1. 一句话定义

**VisionStation 是一套装在检测工位上的 Windows 桌面软件：接工业相机取图，按「配方」里配好的若干检测工具判断零件合格与否，把结论和图片存下来，并把结果实时显示给操作员。**

更短的说法：**它是检测工位的软件本体**——相机是它的眼睛，配方是它的作业指导书，SQLite 是它的台账。

技术形态：.NET 8 + WPF 单体桌面应用，离线运行，不需要服务器、不需要网络、不需要登录。

---

## 2. 它解决什么问题

产线上"看一眼零件合不合格"这件事，靠人做有四个绕不过去的毛病：

| 人的问题 | 软件怎么接 |
|---|---|
| 慢，且会累 | 定时或按钮触发，采图到出结论全自动，人只看结果 |
| 判定不一致，换个人换把尺 | 判定标准写进配方 JSON（阈值、公差、面积下限），同一份配方谁跑都一样 |
| 出了问题查不到证据 | 每帧存一条数据库记录 + 一张原图（证据图，按日期分目录存），NG 件能回溯到当时那一帧 |
| 判了 NG 不知道为什么 NG | 每个工具给出自己的结论与度量值（相似度、实测直径、缺陷面积），落到报告的 `Results` 里 |

它**不追求**替代成熟的商用视觉平台（VisionPro / 海康 VM）。取舍是刻意的：整条链路自己实现，为的是每一处都能解释清楚——为什么这一帧判 NG、为什么这张图没存、为什么关窗口要等一会儿。这也是它作为工程作品的主要价值。

## 3. 谁在用它

软件只有一个界面，但有三类人在用它，关心的东西完全不同：

| 角色 | 在工位上做什么 | 只关心 |
|---|---|---|
| **操作员** | 上班开软件、点开始、看结果、下班关软件 | 现在能不能检、刚才那件是 OK 还是 NG、卡住了怎么办 |
| **工艺/调试工程师** | 换产品时改配方：画 ROI、调阈值、填标定比例 | 改完存哪了、下次启动还在不在、改坏了能不能看出来 |
| **质检/追溯** | 事后查某天的记录、某件为什么判 NG | 记录里有什么字段、图还在不在、能不能对上时间 |

这个划分决定了界面的取舍：默认落在「检测」页（操作员视角），ROI 编辑要按 F2 才进（工程师视角，防止误触），历史与追溯走数据库而不是界面（当前阶段未做回顾页）。

## 4. 六个核心概念

理解这六个词，就理解了这个软件在干什么。

| 概念 | 含义 | 落在哪 |
|---|---|---|
| **零件 / 产品** | 被检对象。当前配方是「金属垫圈检测」 | 配方文件的 `name` |
| **配方（Recipe）** | 一份完整的作业指导书：标定参数 + ROI 列表 + 工具列表与参数。换产品 = 换配方，不改代码 | `src/VisionStation.App/Config/recipes/default.json` |
| **ROI** | 图像上的一块矩形区域，像素坐标。每个工具只在自己那块区域里干活——限定搜索范围，也避免无关区域干扰 | 配方里的 `rois[]` |
| **工具（Tool）** | 一种检测算法，实现统一的 `IVisionTool`。当前四种：模板匹配（有无）、霍夫圆+尺寸（毫米）、Blob（缺陷）、ONNX YOLO（缺陷分类） | `VisionStation.Core/Tools/` |
| **Pipeline** | 按顺序把工具跑一遍，把每个工具的结果汇总成一份报告 | `VisionStation.Core/Pipeline.cs` |
| **标定（Calibration）** | 像素与毫米的换算比例。没有它，"直径 40 像素"对操作员毫无意义；有了它，输出是"实测 12.4mm / 设计 12.7mm / 偏差 0.3mm" | 配方里的 `calibration` |

**判定语义**：报告 `IsOk = 所有工具都 OK`，一项不合格整件不合格；**且结果为空必须判 NG**——一个工具都没跑，不代表合格。

## 5. 一次检测的完整生命周期

### 5.1 软件启动时

```
读配置（appsettings.json）      → 数据根目录、相机模式、存储策略、清理阈值
绑定强类型 Options              → 填错启动期就报错，不静默回落默认值
启动自检 5 项                   → 设备连接 / 数据库 / 存储路径 / 模板文件 / 配方
装配相机与工具                  → 相机三选一（文件 / USB / 海康），工具按配方创建
拉起看门狗                      → 独立进程，主进程异常终止才重启
进主窗口，停在「检测」页
```

自检失败不会让软件装死：失败项写进日志，摘要显示在状态栏，能检就继续检（相机掉了仍可用文件相机验证软件本身是否正常）。

### 5.2 来一件活（一次检测）

```
① 触发          手动点「开始检测」／自动模式定时器（默认 2s）
② 取图          相机 → Mat 原图（File 相机读 TestImages/，海康走 MVS SDK）
③ 检测          Pipeline 逐工具执行，每个工具只吃自己 ROI 内的灰度子图
④ 标注          各工具产出 DrawCommand（框/圆/轮廓）→ 画到原图上
⑤ 存图          按存储策略落盘原图：全存 / 仅 NG / 抽样（标注图只上屏，不落盘）
⑥ 存库          一条 InspectionRecords 记录：总判定 + 各工具结论 + 全量 JSON 快照
⑦ 上屏          原图、标注图、逐工具结论、日志行
```

关键点：**②到⑥整段在后台线程**，UI 线程只做第 ⑦ 步的贴图；位图跨线程前 `Freeze()`；每帧的 `Mat` 用完立刻释放——12MP 彩色帧一帧就是 36MB，5 帧/秒漏释放，几分钟就把非托管内存吃穿。

### 5.3 换产品（换型）

```
F2 进 ROI 编辑器 → 拖画新框 / 拖动 / 右下角缩放 / Delete 删除
→ 点保存 → 写回配方 JSON
→ 工作流重新读配方、取新快照
→ （阈值与标定比例仍在配方文件里改：当前没有参数页）
```

### 5.4 出问题的时候

| 场景 | 软件行为 |
|---|---|
| 相机掉线 | 该帧判失败并记日志，不崩；状态栏与相机页状态变化 |
| 磁盘满 / 目录被删 | 单次失败容忍，**连续失败升级告警**——不能按自动模式的频率安静地丢光 NG 图 |
| 检测算法抛异常 | 该工具记 NG 并继续跑后续工具，不让一颗坏工具废掉整份报告 |
| 配方里工具重名 | 装配期直接抛异常（重名会让结果互相覆盖，NG 被覆盖成假 OK） |
| 主进程崩溃 | 看门狗拉起；窗口期内超次数则不再拉起，写 CRITICAL 等人 |
| 长期运行 | 管家按阈值清理过期记录与图片、监控进程内存 |

## 6. 能力边界

这一节是这个文档最重要的部分。**没做的写没做**，不写"基本可用"。

### 6.1 已实现

| 模块 | 内容 |
|---|---|
| 取图 | 文件相机（仓库内样图，无硬件也能跑）、USB 摄像头、海康工业相机（MVS SDK V4.x 真实接入） |
| 检测 | 模板匹配 / 霍夫圆尺寸测量 / Blob 缺陷 / ONNX YOLO；Pipeline 串联，单工具异常隔离 |
| 标定 | px↔mm 换算，随配方生效 |
| 交互 | 图像缩放平移复位、实时像素坐标、ROI 增删改拖拽缩放保存、手动/自动触发、急停 |
| 存储 | SQLite 记录（含全量结果 JSON）、图片按策略落盘、过期与容量清理 |
| 运维 | 启动自检 5 项、Serilog 文件日志 + 界面日志面板、独立看门狗、崩溃循环保护 |
| 回归 | 黄金样本库 105 张跑批与基线对比（命中 104 / 漏检 1 / 错分 0 / 跨类误报 14 框），有回归退出码 1 可接门禁 |
| 工程 | 测试分两层：`VisionStation.UnitTests`（Core/Devices/Storage/Service 纯逻辑）+ `VisionStation.App.Tests`（组合根与 ViewModel）；另有端到端测试程序与黄金样本跑批器；`ci.cmd` 门禁；self-contained 单目录发布 |

### 6.2 未实现（界面留了口子，功能是空的）

| 项 | 现状 |
|---|---|
| **PLC / 通讯层** | **零代码**。没有 Modbus、没有 TCP 客户端、没有串口、没有 OPC UA。触发只有手动与定时两种；`StatusBarViewModel` 里 PLC 在线状态默认 false，是诚实的 |
| 参数页 | 侧边栏有入口，点了退回检测页。阈值/公差只能改配方 JSON |
| 配方页 | 只有一份默认配方，无列表、无新建、无另存、无版本 |
| 历史页 | 记录已在库里，但界面没有查询/回放；追溯只能开数据库 |
| 日志页 / 系统页 | 侧边栏入口未实现。注意：**日志本身是有的**——主界面下方常驻日志面板（实时滚动、按级别着色），这里缺的只是独立的日志检索页 |
| 相机参数 | 能切相机类型，不能调曝光/增益/触发模式 |
| 标定向导 | 只有手填 px/mm，没有棋盘格标定 |
| 触发来源区分 | 记录里有 `TriggerSource` 字段，但工作流当前写死 `Manual`——定时触发也记成手动。字段在，语义没做到 |

### 6.3 明确不做（不是欠账，是划出去的）

| 不做 | 原因 |
|---|---|
| 通用视觉平台（脚本、拖拽流程编排、多产品工程管理） | 那是 VisionPro/VM 的地盘；做成半个平台反而不如把单条链路做扎实 |
| 训练/标注工具 | 模型是外部训好的 ONNX，本软件只做推理 |
| MES / ERP 对接、云端同步 | 单机离线是这个软件的定位前提；一旦联网，权限、审计、断网降级全要重做 |
| 多相机多工位 | 当前是单工位单相机模型，多工位是另一个产品形态 |
| 用户/权限体系 | 产线单机、物理隔离场景，先不引入账号成本 |

## 7. 它不是什么

- **不是算法库**：OpenCV 与 ONNX 是它用的工具，它的产品是"一条能上工位的检测流程"，不是几个检测函数。
- **不是框架或脚手架**：没有插件系统、没有规则引擎、没有自研 DI/消息总线。所有抽象只服务当前这一条链路。
- **不是演示程序**：有持久化、有崩溃恢复、有长期运行的内存与磁盘治理、有算法回归基线——这些是"能连续跑三个月"和"能跑通一次 demo"的区别。
- **不是 Web 应用套壳**：它是长驻单进程、唯一 UI 线程、有状态的桌面程序，所以线程归属与生命周期是它的主要复杂度来源（见 `docs/WPF开发规范.md`）。

## 8. 判定"这个项目做完了"的标准

不按代码行数、不按功能列表，按**能回答的问题**：

1. 换一个零件，能不能只改配方不动代码？（能，但改阈值要手改 JSON → 参数页是欠账）
2. 一件被判 NG，能不能说清是哪个工具、什么数值、超了多少？（能）
3. 保留期内的任意一件，还能不能查到当时的结论和那张图？（能：库里有记录、盘上有图；超出保留期——默认 30 天——会被管家按阈值清掉，这是策略不是丢失。界面上没有查询，只能查库）
4. 软件连续跑一周，会不会内存涨、磁盘满、崩了没人管？（有管家与看门狗兜底）
5. 改了算法，是变好还是变坏，有没有数字说话？（有，黄金样本库三态对比）
6. 关窗口时正在检测的那一帧会不会被撕掉？（不会，等在途工作收尾后才退出）

六条全部成立即 V1 完成。当前明确的欠账是两条：**参数与阈值没有界面**（只能改 JSON）、**历史没有查询界面**（只能查库）；其余成立。

## 9. 术语表

| 词 | 含义 |
|---|---|
| OK / NG | 合格 / 不合格。总判定 = 所有工具都 OK |
| 过杀 / 误报 | 好件被判 NG |
| 漏检 | 坏件被判 OK——比过杀严重得多，是验收时优先压的指标 |
| 三态判定 | 命中（检出且分类对）/ 错分（检出但认错类）/ 漏检（一个框都没有） |
| 配方快照 | 一次检测用的 ROI 与参数，工作流持有一份引用，后台跑帧时不被编辑器改写 |
| 在途工作 | 关闭窗口时还在跑的检测帧，必须等它收尾或超时才退出 |
| 数据根 | 所有可写数据（数据库/日志/图片）的根目录，可用 `--data-root` 指定，便携部署用 |
